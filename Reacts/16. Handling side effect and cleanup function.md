Handling side effects in React means:

> **Start some synchronization with the outside world, and clean it up when that synchronization is no longer needed.**

The standard pattern is:

```jsx
useEffect(() => {
  // setup side effect

  return () => {
    // cleanup side effect
  };
}, [dependencies]);
```

The most important mental model is:

```text
Setup
  ↓
Use external resource
  ↓
Cleanup
```

# 1. What kinds of things need cleanup?

Common examples:

```text
Event listeners
Timers
Intervals
WebSocket connections
Subscriptions
Observers
Third-party libraries
Pending network requests
```

If you create something external, ask:

> Do I need to undo or stop it later?

If yes, you probably need a cleanup function.

# 2. Basic cleanup syntax

```jsx
useEffect(() => {
  console.log("setup");

  return () => {
    console.log("cleanup");
  };
}, []);
```

The function returned from `useEffect` is the cleanup function.

Important:

```jsx
return () => {
  // cleanup
};
```

not:

```jsx
return cleanup();
```

You must return the function, not execute it immediately.

# 3. When does cleanup run?

Cleanup runs in two important situations.

First, when the component is removed:

```text
Component mounts
   ↓
Effect setup

Component unmounts
   ↓
Effect cleanup
```

Second, when dependencies change:

```text
Effect setup with old dependency
        ↓
dependency changes
        ↓
old cleanup runs
        ↓
new setup runs
```

This second case is extremely important.

# 4. Example with dependency change

Suppose:

```jsx
function ChatRoom({ roomId }) {
  useEffect(() => {
    console.log("Connect:", roomId);

    return () => {
      console.log("Disconnect:", roomId);
    };
  }, [roomId]);

  return <h1>{roomId}</h1>;
}
```

Initially:

```text
roomId = "general"
```

React does:

```text
Connect: general
```

Then:

```text
roomId = "support"
```

React does:

```text
Disconnect: general
Connect: support
```

Then component disappears:

```text
Disconnect: support
```

So cleanup does not mean only:

> component destroyed

It also means:

> previous effect is no longer valid.

# 5. Event listener example

Without cleanup:

```jsx
useEffect(() => {
  window.addEventListener("resize", handleResize);
}, []);
```

Problem:

If the component mounts and unmounts repeatedly, listeners may remain attached.

Correct:

```jsx
useEffect(() => {
  function handleResize() {
    console.log(window.innerWidth);
  }

  window.addEventListener("resize", handleResize);

  return () => {
    window.removeEventListener("resize", handleResize);
  };
}, []);
```

Think:

```text
addEventListener
      ↓
must pair with
      ↓
removeEventListener
```

# 6. Why the same function reference matters

This is important.

Bad:

```jsx
useEffect(() => {
  window.addEventListener("resize", () => {
    console.log("resize");
  });

  return () => {
    window.removeEventListener("resize", () => {
      console.log("resize");
    });
  };
}, []);
```

These two arrow functions are different function objects.

So removal may fail.

Better:

```jsx
useEffect(() => {
  function handleResize() {
    console.log("resize");
  }

  window.addEventListener("resize", handleResize);

  return () => {
    window.removeEventListener("resize", handleResize);
  };
}, []);
```

Now the same function reference is used.

# 7. Timer example

Suppose:

```jsx
useEffect(() => {
  setInterval(() => {
    console.log("tick");
  }, 1000);
}, []);
```

The interval keeps running.

Better:

```jsx
useEffect(() => {
  const intervalId = setInterval(() => {
    console.log("tick");
  }, 1000);

  return () => {
    clearInterval(intervalId);
  };
}, []);
```

Pair:

```text
setInterval
   ↓
clearInterval
```

# 8. Timeout example

```jsx
useEffect(() => {
  const timeoutId = setTimeout(() => {
    console.log("Done");
  }, 3000);

  return () => {
    clearTimeout(timeoutId);
  };
}, []);
```

Pair:

```text
setTimeout
  ↓
clearTimeout
```

# 9. Subscription example

Imagine:

```jsx
useEffect(() => {
  const subscription = subscribeToMessages();

```

This is a very common pattern.

Think:

```text

```

# 10. WebSocket example

```jsx
useEffect(() => {
  const socket = new WebSocket(
    "wss://example.com/socket"
  );

  socket.addEventListener("open", () => {
    console.log("Connected");
  });

  return () => {
    socket.close();
  };
}, []);
```

Pair:

```text

   ↓

```

# 11. Side effects should usually be symmetrical

A useful rule:

> Cleanup should undo whatever setup did.

Examples:

```text
Setup                     Cleanup

addEventListener     →    removeEventListener

setInterval          →    clearInterval

setTimeout           →    clearTimeout

subscribe            →    unsubscribe

connect              →    disconnect

observe              →    unobserve

open socket          →    close socket
```

This symmetry is one of the best ways to reason about Effects.

# 12. Example with DOM observer

Suppose:

```jsx
useEffect(() => {
  const observer = new ResizeObserver(() => {

  });

  observer.observe(element);

  return () => {
    observer.disconnect();
  };
}, []);
```

Again:

```text
observe
   ↓
disconnect
```

# 13. Network requests and cleanup

Fetch requests are a little different.

Suppose:

```jsx
useEffect(() => {
  fetch(`/api/users/${userId}`)
    .then(res => res.json())
    .then(data => setUser(data));
}, [userId]);
```

Potential problem:

```text
userId = 1
↓
request 1 starts

userId = 2
↓
request 2 starts

request 2 finishes
↓
show user 2

request 1 finishes later
↓
show user 1 incorrectly
```

This is called a race condition.

One solution is `AbortController`.

```jsx
useEffect(() => {
  const controller = new AbortController();

  async function loadUser() {
    try {
      const response = await fetch(
        `/api/users/${userId}`,
        {
          signal: controller.signal
        }
      );

      const data = await response.json();
      setUser(data);
    } catch (error) {
      if (error.name !== "AbortError") {
        console.error(error);
      }
    }
  }

  loadUser();

  return () => {
    controller.abort();
  };
}, [userId]);
```

Now when `userId` changes:

```text
old request
   ↓
abort
   ↓
new request starts
```

This is a good cleanup example.

# 14. Why cleanup is important for fetch

Cleanup can help prevent:

```text
Stale responses
Race conditions
Unnecessary work
Updates from obsolete requests
```

You do not need to abort every fetch blindly, but it is useful when a request becomes irrelevant after dependencies change or the component is removed.

# 15. Example with a flag

You may also see:

```jsx
useEffect(() => {
  let ignore = false;

  async function loadData() {
    const response = await fetch("/api/data");
    const data = await response.json();

    if (!ignore) {
      setData(data);
    }
  }

  loadData();

  return () => {
    ignore = true;
  };
}, []);
```

This does not cancel the network request.

Instead, it says:

> Ignore the result if this Effect is no longer current.

Useful distinction:

```text
AbortController
→ stops request if possible

ignore flag
→ allows request to finish but ignores result
```

# 16. Side effect inside event handler vs useEffect

This is a very important distinction.

Suppose the user clicks:

```jsx
<button onClick={handleDelete}>
  Delete
</button>
```

Then:

```jsx
function handleDelete() {
  fetch("/api/delete", {
    method: "DELETE"
  });
}
```

This should usually stay in the event handler.

You do not need:

```jsx
useEffect(() => {
  if (shouldDelete) {
    deleteItem();
  }
}, [shouldDelete]);
```

Why?

Because the reason for the effect is already known:

```text
User clicked Delete
```

Use `useEffect` when synchronization is caused by the component's rendered state, not when a specific event directly caused the action.

# 17. Common mistake: cleanup updates state

Avoid patterns like:

```jsx
useEffect(() => {
  return () => {
    setCount(0);
  };
}, []);
```

Usually cleanup should release external resources, not perform arbitrary state management.

Ask:

> What external setup am I undoing?

If the answer is "none," the cleanup may be unnecessary.

# 18. Common mistake: cleanup without setup

This is suspicious:

```jsx
useEffect(() => {
  return () => {
    console.log("cleanup");
  };
}, []);
```

A cleanup function generally exists because setup created something that must be undone.

Think:

```text
No setup
↓
Why cleanup?
```

Not always invalid, but it should make you question the design.

# 19. Strict Mode and cleanup

In development, React Strict Mode may do something like:

```text
setup
↓
cleanup
↓
setup again
```

This intentionally tests whether your Effect is safe.

For example:

```jsx
useEffect(() => {
  const connection = connect();

  return () => {
    connection.disconnect();
  };
}, []);
```

If this works correctly:

```text
connect
disconnect
connect
```

then your Effect is likely well designed.

If the second connection breaks, the cleanup is probably incomplete.

# 20. Example: bad connection effect

Bad:

```jsx
useEffect(() => {
  connectToServer();
}, []);
```

If React tests the Effect twice in development:

```text
connect
connect
```

you may accidentally create two connections.

Better:

```jsx
useEffect(() => {
  const connection = connectToServer();

  return () => {
    connection.disconnect();
  };
}, []);
```

Now:

```text
connect
disconnect
connect
```

is safe.

# 21. Dependencies and cleanup work together

Suppose:

```jsx
useEffect(() => {
  const connection = connect(roomId);

  return () => {
    connection.disconnect();
  };
}, [roomId]);
```

This is a complete synchronization unit.

Think:

```text
roomId
  ↓
setup using roomId
  ↓
roomId changes
  ↓
cleanup previous room
  ↓
setup next room
```

Dependencies are not just about "when to run."

They define which values the synchronization depends on.

# 22. Full example: online/offline listener

```jsx
import {
  useEffect,
  useState
} from "react";

function Status() {
  const [isOnline, setIsOnline] = useState(
    navigator.onLine
  );

  useEffect(() => {
    function handleOnline() {
      setIsOnline(true);
    }

    function handleOffline() {
      setIsOnline(false);
    }

    window.addEventListener(
      "online",
      handleOnline
    );

    window.addEventListener(
      "offline",
      handleOffline
    );

    return () => {
      window.removeEventListener(
        "online",
        handleOnline
      );

      window.removeEventListener(
        "offline",
        handleOffline
      );
    };
  }, []);

  return (
    <p>
      {isOnline ? "Online" : "Offline"}
    </p>
  );
}
```

This example contains the full pattern:

```text
Initial state
↓
Effect setup
↓
External event listeners
↓
State updates
↓
Cleanup
```

# 23. Full example: timer with dependency

```jsx
function AutoSave({ documentId }) {
  useEffect(() => {
    const intervalId = setInterval(() => {
      saveDocument(documentId);
    }, 5000);

    return () => {
      clearInterval(intervalId);
    };
  }, [documentId]);

  return null;
}
```

If:

```text
documentId = 10
```

timer saves document 10.

Then `documentId` changes:

```text
cleanup timer for document 10
↓
start timer for document 11
```

This is exactly what cleanup is for.

# 24. Common interview questions

### What is a cleanup function in `useEffect`?

> A cleanup function is the function returned from an Effect. React calls it before re-running the Effect with changed dependencies and when the component is unmounted.

### Why do we need cleanup?

> To release external resources and undo synchronization, such as removing event listeners, clearing timers, disconnecting subscriptions, or canceling obsolete requests.

### When does cleanup run?

Two key times:

```text
Before the Effect runs again because dependencies changed

When the component unmounts
```

### Should every Effect return cleanup?

No.

Only if the Effect creates something that needs to be undone.

For example:

```jsx
useEffect(() => {
  document.title = title;
}, [title]);
```

usually does not need cleanup.

### What should cleanup do?

> It should normally undo the setup performed by the Effect.

### Can cleanup run even if the component is not unmounting?

Yes.

If dependencies change, React runs the previous cleanup before the new setup.

### Why does React Strict Mode run setup and cleanup twice in development?

> To detect Effects that are not safely reversible or that leak resources.

# 25. The mental model to remember

Think of every Effect as a small lifecycle:

```text
Dependency values
      ↓
Effect setup
      ↓
External synchronization
      ↓
Dependency changes
      ↓
Cleanup old synchronization
      ↓
Setup new synchronization
```

And at the end:

```text
Component removed
      ↓
Final cleanup
```

The most useful question before writing cleanup is:

> **What did my setup create, subscribe to, start, connect to, or register?**

Then write the opposite operation.

```text
Start something
→ stop it

Subscribe
→ unsubscribe

Connect
→ disconnect

Add
→ remove
```

If you understand that setup/cleanup symmetry, you understand the core of side-effect management in React.
