**Prop drilling** happens when you pass data through several intermediate components that do not actually need that data, just so a deeply nested component can receive it.

A simple definition:

> **Prop drilling = passing props through unnecessary component levels.**

## 1. Start with a normal example

Imagine:

```text
App
 ↓
Dashboard
 ↓
Layout
 ↓
Sidebar
 ↓
UserProfile
```

Suppose only `UserProfile` needs:

```text
user
```

But `user` lives in `App`.

You may end up doing this:

```jsx
function App() {
  const user = {
    name: "John",
    role: "Admin"
  };

  return <Dashboard user={user} />;
}
```

Then:

```jsx
function Dashboard({ user }) {
  return <Layout user={user} />;
}
```

Then:

```jsx
function Layout({ user }) {
  return <Sidebar user={user} />;
}
```

Then:

```jsx
function Sidebar({ user }) {
  return <UserProfile user={user} />;
}
```

Finally:

```jsx
function UserProfile({ user }) {
  return (
    <div>
      <h2>{user.name}</h2>
      <p>{user.role}</p>
    </div>
  );
}
```

Look at the problem:

```text
Dashboard
Layout
Sidebar
```

do not use `user`.

They only forward it.

That is prop drilling.

---

# 2. Why is prop drilling a problem?

Prop drilling is not automatically wrong.

For one or two levels:

```text
Parent
 ↓
Child
 ↓
Grandchild
```

it may be perfectly fine.

The problem appears when:

```text
Many levels
Many props
Many unrelated components
```

For example:

```text
App
 ↓ user, theme, language, permissions
Dashboard
 ↓ user, theme, language, permissions
Layout
 ↓ user, theme, language, permissions
Sidebar
 ↓ user, theme, language, permissions
Profile
```

Now intermediate components become cluttered.

You get:

```jsx
function Layout({
  user,
  theme,
  language,
  permissions
}) {
  return (
    <Sidebar
      user={user}
      theme={theme}
      language={language}
      permissions={permissions}
    />
  );
}
```

Even though `Layout` does not care about any of them.

---

# 3. The mental problem

Normally React data flows like:

```text
Parent
 ↓
Child
```

That is good.

Prop drilling becomes annoying when the actual need is:

```text
App
 ↓
 ↓
 ↓
 ↓
DeepChild
```

but every component in between must participate.

So the question becomes:

> How can a deep component access shared data without every intermediate component forwarding it?

One major answer is:

> **React Context**

---

# 4. First solution: put state closer to where it is needed

Before using Context, always ask:

> Does this state really need to be at the top?

Suppose:

```text
App
├── Header
└── Dashboard
    ├── SearchBar
    └── ProductList
```

Only:

```text
SearchBar
ProductList
```

need `search`.

Bad:

```jsx
function App() {
  const [search, setSearch] = useState("");
}
```

because `Header` does not care.

Better:

```jsx
function Dashboard() {
  const [search, setSearch] = useState("");

  return (
    <>
      <SearchBar
        search={search}
        onSearchChange={setSearch}
      />

      <ProductList search={search} />
    </>
  );
}
```

So before solving prop drilling with a tool, ask:

```text
Can I move the state down?
```

This is often the best solution.

---

# 5. Solution 2: Component composition

Sometimes you can avoid forwarding props by passing whole components as children.

Suppose:

```jsx
function App() {
  const user = {
    name: "John"
  };

  return (
    <Layout user={user} />
  );
}
```

Then:

```jsx
function Layout({ user }) {
  return (
    <Sidebar user={user} />
  );
}
```

Instead, you could compose:

```jsx
function App() {
  const user = {
    name: "John"
  };

  return (
    <Layout
      sidebar={
        <UserProfile user={user} />
      }
    />
  );
}
```

Then:

```jsx
function Layout({ sidebar }) {
  return (
    <div>
      <main>Main Content</main>

      <aside>
        {sidebar}
      </aside>
    </div>
  );
}
```

Now `Layout` does not need to know anything about:

```text
user
```

It only receives ready-made UI.

This can avoid unnecessary prop forwarding.

---

# 6. Solution 3: React Context

This is the most common answer for genuine deep shared state.

Context allows a parent to make a value available to many descendants without passing it manually through every intermediate component.

The architecture becomes:

```text
App
 ↓
UserContext.Provider
 ↓
Dashboard
 ↓
Layout
 ↓
Sidebar
 ↓
UserProfile
```

`Dashboard`, `Layout`, and `Sidebar` do not need to receive `user`.

`UserProfile` can read it directly from context.

---

# 7. Basic Context example

Create:

```jsx
import { createContext } from "react";

const UserContext = createContext(null);
```

Then provide a value:

```jsx
function App() {
  const user = {
    name: "John",
    role: "Admin"
  };

  return (
    <UserContext.Provider value={user}>
      <Dashboard />
    </UserContext.Provider>
  );
}
```

Now intermediate components:

```jsx
function Dashboard() {
  return <Layout />;
}

function Layout() {
  return <Sidebar />;
}

function Sidebar() {
  return <UserProfile />;
}
```

No `user` prop anywhere.

Finally:

```jsx
import { useContext } from "react";

function UserProfile() {
  const user = useContext(UserContext);

  return (
    <div>
      <h2>{user.name}</h2>
      <p>{user.role}</p>
    </div>
  );
}
```

Now the flow is:

```text
Provider
   ↓
Context
   ↓
Deep child reads value
```

No prop drilling.

---

# 8. What does `createContext()` do?

This:

```jsx
const UserContext = createContext(null);
```

creates a Context object.

Think:

```text
UserContext
=
shared communication channel
```

It does not automatically store state.

It simply allows values to be provided and consumed.

---

# 9. What does the Provider do?

This:

```jsx
<UserContext.Provider value={user}>
  <Dashboard />
</UserContext.Provider>
```

means:

> Any descendant component can access this `user` context value.

Conceptually:

```text
Provider
  value = user
      ↓
All descendants
```

---

# 10. What does `useContext()` do?

This:

```jsx
const user = useContext(UserContext);
```

means:

> Find the nearest `UserContext` provider above me and give me its value.

So:

```jsx
function UserProfile() {
  const user = useContext(UserContext);
}
```

does not care whether the provider is:

```text
1 level above
5 levels above
20 levels above
```

---

# 11. Context with state

Context becomes more useful when the value changes.

Example:

```jsx
import {
  createContext,
  useContext,
  useState
} from "react";

const ThemeContext = createContext(null);

function App() {
  const [theme, setTheme] = useState("light");

  return (
    <ThemeContext.Provider
      value={{
        theme,
        setTheme
      }}
    >
      <Page />
    </ThemeContext.Provider>
  );
}
```

Deep child:

```jsx
function ThemeButton() {
  const {
    theme,
    setTheme
  } = useContext(ThemeContext);

  function handleToggle() {
    setTheme(
      theme === "light"
        ? "dark"
        : "light"
    );
  }

  return (
    <button onClick={handleToggle}>
      Current Theme: {theme}
    </button>
  );
}
```

Now any descendant can:

```text
Read theme
Change theme
```

without prop drilling.

---

# 12. Better structure: separate Context file

In real projects, you usually do not put everything inside `App.jsx`.

Example:

```text
src/
├── context/
│   └── UserContext.jsx
│
├── components/
├── App.jsx
└── main.jsx
```

`UserContext.jsx`:

```jsx
import {
  createContext,
  useContext,
  useState
} from "react";

const UserContext = createContext(null);

export function UserProvider({ children }) {
  const [user, setUser] = useState({
    name: "John",
    role: "Admin"
  });

  return (
    <UserContext.Provider
      value={{
        user,
        setUser
      }}
    >
      {children}
    </UserContext.Provider>
  );
}

export function useUser() {
  return useContext(UserContext);
}
```

Now:

```jsx
function App() {
  return (
    <UserProvider>
      <Dashboard />
    </UserProvider>
  );
}
```

And deep child:

```jsx
function UserProfile() {
  const { user } = useUser();

  return (
    <h2>{user.name}</h2>
  );
}
```

This is much cleaner.

---

# 13. Why create a custom Hook?

Instead of repeatedly writing:

```jsx
useContext(UserContext)
```

you can create:

```jsx
function useUser() {
  return useContext(UserContext);
}
```

Then:

```jsx
const { user } = useUser();
```

Benefits:

```text
Cleaner API
Less repeated code
Context implementation is hidden
Easier to change later
```

This is a common professional pattern.

---

# 14. Context is not always the answer

This is very important.

Some beginners learn Context and immediately put everything into global context.

That is not good design.

Do not put:

```text
Every button state
Every modal state
Every form field
Every local input
```

into Context.

For example:

```jsx
const [isMenuOpen, setIsMenuOpen]
```

may belong only in:

```text
Header
```

Keep it there.

---

# 15. Local state vs lifted state vs context

Use this decision model.

### Local state

If only one component needs it:

```text
Component
└── state
```

Example:

```text
Password visibility
Local modal
Input text
```

Use:

```jsx
useState()
```

inside that component.

---

### Lifted state

If nearby siblings need it:

```text
Parent
├── Child A
└── Child B
```

Put state in:

```text
Parent
```

Then use props.

---

### Context

If many distant descendants need the same data:

```text
App
├── Header
├── Dashboard
│   ├── Sidebar
│   └── Content
└── Settings
```

and they all need:

```text
user
theme
language
```

Context may make sense.

---

# 16. A practical decision tree

Ask:

```text
Does only one component need the state?
        ↓
       Yes
        ↓
Keep it local
```

If no:

```text
Do nearby siblings need it?
        ↓
       Yes
        ↓
Lift state to common parent
```

If no:

```text
Do many deeply nested components need it?
        ↓
       Yes
        ↓
Consider Context
```

If the application becomes much more complex:

```text
Consider a dedicated state library
```

---

# 17. What is "global state"?

You may hear:

```text
Global state
```

This means data needed across many parts of the application.

Examples:

```text
Authenticated user
Theme
Language
Shopping cart
Permissions
Application settings
```

Context can handle many simple global-state cases.

---

# 18. Context vs props

Props:

```text
Explicit
Parent → Child
```

Example:

```jsx
<UserProfile user={user} />
```

Context:

```text
Implicit shared access
Provider → any descendant
```

Example:

```jsx
const user = useContext(UserContext);
```

Props are usually easier to understand and trace.

So don't replace all props with Context.

---

# 19. Context can cause re-renders

Suppose:

```jsx
<UserContext.Provider
  value={{
    user,
    theme,
    cart
  }}
>
```

If the context value changes, components consuming that context may re-render.

If you put too much unrelated state into one giant context:

```text
AppContext
├── user
├── theme
├── cart
├── search
├── modal
├── notifications
├── form
└── everything
```

you can make the application harder to manage.

Better:

```text
UserContext
ThemeContext
CartContext
```

when those concerns are truly independent.

---

# 20. Bad giant context

Avoid:

```jsx
<AppContext.Provider
  value={{
    user,
    theme,
    cart,
    modal,
    filters,
    notifications,
    search,
    language,
    settings
  }}
>
```

unless the architecture genuinely justifies it.

This can become a "global junk drawer."

---

# 21. When Context becomes insufficient

For larger applications with complex shared state, developers may use libraries such as:

```text
Redux Toolkit
Zustand
Jotai
```

You do not need these yet.

First understand:

```text
useState
Props
Lifting state
Context
```

Those concepts make state-management libraries much easier later.

---

# 22. Context does not magically replace state

Important:

```jsx
createContext()
```

does not create state.

You still use things like:

```jsx
useState()
```

Example:

```jsx
const [user, setUser] = useState(null);
```

Context simply distributes:

```text
user
setUser
```

to descendants.

So:

```text
useState
=
stores state
```

```text
Context
=
shares values
```

# 23. Another solution: pass JSX instead of data

This composition technique is underrated.

Bad drilling:

```text
App
 ↓ user
Layout
 ↓ user
Sidebar
 ↓ user
Profile
```

Alternative:

```jsx
function App() {
  return (
    <Layout
      sidebar={
        <UserProfile user={user} />
      }
    />
  );
}
```

Now:

```jsx
function Layout({ sidebar }) {
  return (
    <div>
      <main>Content</main>
      <aside>{sidebar}</aside>
    </div>
  );
}
```

`Layout` no longer needs knowledge of `user`.

This solves some forms of prop drilling without Context.

# 24. Props drilling example with event handler

It is not only data.

You can also drill functions.

Example:

```text
App
 ↓ onLogout
Header
 ↓ onLogout
Nav
 ↓ onLogout
ProfileMenu
```

Even if:

```text
Header
Nav
```

do not need `onLogout`.

Context can help here too.

Example:

```jsx
<AuthContext.Provider
  value={{
    user,
    logout
  }}
>
```

Then deep component:

```jsx
function ProfileMenu() {
  const { logout } = useContext(AuthContext);

  return (
    <button onClick={logout}>
      Logout
    </button>
  );
}
```

# 25. Complete before-and-after example

## Before: prop drilling

```jsx
function App() {
  const [theme, setTheme] = useState("light");

  return (
    <Dashboard
      theme={theme}
      setTheme={setTheme}
    />
  );
}

function Dashboard({
  theme,
  setTheme
}) {
  return (
    <Layout
      theme={theme}
      setTheme={setTheme}
    />
  );
}

function Layout({
  theme,
  setTheme
}) {
  return (
    <Sidebar
      theme={theme}
      setTheme={setTheme}
    />
  );
}

function Sidebar({
  theme,
  setTheme
}) {
  return (
    <ThemeButton
      theme={theme}
      setTheme={setTheme}
    />
  );
}
```

That is drilling.

---

## After: Context

```jsx
import {
  createContext,
  useContext,
  useState
} from "react";

const ThemeContext = createContext(null);

function App() {
  const [theme, setTheme] = useState("light");

  return (
    <ThemeContext.Provider
      value={{
        theme,
        setTheme
      }}
    >
      <Dashboard />
    </ThemeContext.Provider>
  );
}

function Dashboard() {
  return <Layout />;
}

function Layout() {
  return <Sidebar />;
}

function Sidebar() {
  return <ThemeButton />;
}

function ThemeButton() {
  const {
    theme,
    setTheme
  } = useContext(ThemeContext);

  return (
    <button
      onClick={() =>
        setTheme(
          theme === "light"
            ? "dark"
            : "light"
        )
      }
    >
      {theme}
    </button>
  );
}
```

Now:

```text
Dashboard
Layout
Sidebar
```

do not know anything about theme.

Much cleaner.

# Common Interview Questions

### 1. What is prop drilling?

> Prop drilling is the process of passing props through multiple intermediate components that do not need those values themselves, only so a deeply nested component can receive them.

---

### 2. Is prop drilling always bad?

No.

> Passing props through a few levels is normal React. It becomes problematic when many intermediate components forward unrelated props and the component tree becomes difficult to maintain.

---

### 3. How can we solve prop drilling?

Common approaches:

```text
Move state closer to where it is needed
Lift state only to nearest common parent
Use component composition
Use React Context
Use a state-management library for complex global state
```

---

### 4. What is React Context?

> Context lets a parent provide a value to deeply nested descendants without manually passing that value through every intermediate component.

---

### 5. What does `useContext()` do?

> It reads the value from the nearest matching Context provider above the component.

---

### 6. Does Context replace `useState`?

No.

> `useState` stores state. Context shares values across descendants.

---

### 7. When should you use Context?

Good examples:

```text
Theme
Authentication
Current user
Language
Permissions
Shopping cart
```

when many distant components need the same value.

---

### 8. When should you avoid Context?

Avoid it for state that is:

```text
Highly local
Used by only one or two nearby components
Temporary form input
Simple modal state
```

---

### 9. What is the difference between lifting state and Context?

> Lifting state moves shared state to a common parent and passes it through props. Context allows descendants to access shared values without manually forwarding those props through every intermediate component.

---

### 10. What is global state?

> Global state is application data that is required across multiple distant areas of the component tree.

---

# The mental model to remember

Start with the simplest solution.

```text
Only one component needs it
        ↓
Local state
```

```text
Nearby siblings need it
        ↓
Lift state
```

```text
Deeply nested components need it
        ↓
Context
```

```text
Very complex global state
        ↓
State-management library
```

And remember this distinction:

```text
useState
=
Store state

Props
=
Pass data explicitly

Context
=
Share data deeply

Redux/Zustand/etc.
=
Manage more complex shared state
```

The most important lesson is not **"prop drilling is bad."** The better rule is:

> **Use normal props until the data flow becomes unnecessarily repetitive. Then solve the actual structural problem with better state placement, composition, Context, or—only when justified—a state-management library.**
