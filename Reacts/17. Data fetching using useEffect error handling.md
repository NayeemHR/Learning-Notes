Data fetching is where several concepts you have already learned come together:

```text
useState
   +
useEffect
   +
async / await
   +
error handling
   +
cleanup
```

The core idea is:

> **When a component needs to stay synchronized with remote data, an Effect can start the request, store the result in state, and clean up obsolete requests.**

However, modern React guidance is important: fetching directly inside `useEffect` is valid, but for larger production applications React recommends framework data-loading mechanisms or client-side caching libraries when available because they solve caching, deduplication, race conditions, and network waterfalls more effectively. ([React][1])

# 1. First understand the data-fetching flow

Imagine this API:

```text
https://api.example.com/users
```

It returns:

```json
[
  {
    "id": 1,
    "name": "John"
  },
  {
    "id": 2,
    "name": "Sarah"
  }
]
```

Our React component needs to do:

```text
Component renders
      ↓
useEffect runs
      ↓
Fetch API
      ↓
Wait for response
      ↓
Convert response to JSON
      ↓
Store data in state
      ↓
Component re-renders
      ↓
Display data
```

Usually we also need:

```text
Loading
Success
Error
```

So our state might be:

```jsx
const [users, setUsers] = useState([]);
const [loading, setLoading] = useState(true);
const [error, setError] = useState(null);
```

---

# 2. Old/common approach: `.then()`

A lot of older tutorials show this:

```jsx
import { useEffect, useState } from "react";

function Users() {
  const [users, setUsers] = useState([]);

  useEffect(() => {
    fetch("https://api.example.com/users")
      .then(response => response.json())
      .then(data => {
        setUsers(data);
      });
  }, []);

  return (
    <div>
      {users.map(user => (
        <p key={user.id}>
          {user.name}
        </p>
      ))}
    </div>
  );
}
```

This works.

The flow:

```text
fetch()
   ↓
Promise
   ↓
.then(response)
   ↓
response.json()
   ↓
Promise
   ↓
.then(data)
   ↓
setUsers(data)
```

Remember:

```text
fetch()
does not immediately return your data
```

It returns a:

```text
Promise
```

---

# 3. What is wrong with the simple old example?

This:

```jsx
useEffect(() => {
  fetch(url)
    .then(response => response.json())
    .then(data => setUsers(data));
}, []);
```

is missing several important things:

```text
Loading state
HTTP error checking
Network error handling
Cleanup
Race-condition protection
```

So it is okay for understanding the concept, but not a strong production pattern.

---

# 4. Old approach with error handling

A better `.then()` version:

```jsx
import { useEffect, useState } from "react";

function Users() {
  const [users, setUsers] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    fetch("https://api.example.com/users")
      .then(response => {
        if (!response.ok) {
          throw new Error(
            `HTTP error: ${response.status}`
          );
        }

        return response.json();
      })
      .then(data => {
        setUsers(data);
      })
      .catch(error => {
        setError(error.message);
      })
      .finally(() => {
        setLoading(false);
      });
  }, []);

  if (loading) {
    return <p>Loading...</p>;
  }

  if (error) {
    return <p>Error: {error}</p>;
  }

  return (
    <div>
      {users.map(user => (
        <p key={user.id}>
          {user.name}
        </p>
      ))}
    </div>
  );
}
```

Now we have:

```text
.then()
→ success handling

.catch()
→ error handling

.finally()
→ always executes
```

---

# 5. Very important: `fetch()` does not reject for every HTTP error

This catches many beginners.

Suppose the server returns:

```text
404
```

or:

```text
500
```

`fetch()` does not automatically treat every HTTP error response like a rejected Promise.

So this isn't enough:

```jsx
fetch(url)
  .then(response => response.json())
  .catch(error => {
    // ...
  });
```

You should check:

```jsx
response.ok
```

Example:

```jsx
if (!response.ok) {
  throw new Error(
    `Request failed: ${response.status}`
  );
}
```

Then your `.catch()` or `catch` block can handle it.

---

# 6. Modern syntax: `async / await`

Today, many developers find `async/await` easier to read.

Instead of:

```jsx
fetch(url)
  .then(response => response.json())
  .then(data => setUsers(data))
  .catch(error => setError(error.message));
```

we can write:

```jsx
try {
  const response = await fetch(url);

  const data = await response.json();

  setUsers(data);
} catch (error) {
  setError(error.message);
}
```

Much more sequential.

---

# 7. But don't make the Effect callback `async`

This is a common mistake.

Avoid:

```jsx
useEffect(async () => {
  const response = await fetch(url);
}, []);
```

Why?

An `async` function automatically returns a Promise.

But React expects an Effect callback to return either:

```text
nothing
```

or:

```text
a cleanup function
```

not a Promise.

So instead:

```jsx
useEffect(() => {
  async function fetchUsers() {
    // await here
  }

  fetchUsers();
}, []);
```

React's documentation uses this inner-async-function pattern when demonstrating `async/await` inside Effects. ([React][2])

---

# 9. Modern version with loading and errors

A better version:

```jsx
import { useEffect, useState } from "react";

function Users() {
  const [users, setUsers] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    async function fetchUsers() {
      try {
        setLoading(true);
        setError(null);

        const response = await fetch(
          "https://api.example.com/users"
        );

        if (!response.ok) {
          throw new Error(
            `Request failed: ${response.status}`
          );
        }

        const data = await response.json();

        setUsers(data);
      } catch (error) {
        setError(error.message);
      } finally {
        setLoading(false);
      }
    }

    fetchUsers();
  }, []);

  if (loading) {
    return <p>Loading...</p>;
  }

  if (error) {
    return <p>Error: {error}</p>;
  }

  return (
    <div>
      {users.map(user => (
        <p key={user.id}>
          {user.name}
        </p>
      ))}
    </div>
  );
}
```

Understand these three blocks:

```jsx
try {
  // code that might fail
}
```

```jsx
catch (error) {
  // failure
}
```

```jsx
finally {
  // always run
}
```

---

# 10. Why `finally` is useful

Without `finally`, you might write:

```jsx
try {
  // success

  setLoading(false);
} catch (error) {
  // failure

  setLoading(false);
}
```

Duplicated.

Instead:

```jsx
finally {
  setLoading(false);
}
```

runs whether:

```text
Success
or
Failure
```

---

# 11. The three main UI states

When fetching data, always think:

```text
1. Loading
2. Error
3. Success
```

Example:

```jsx
if (loading) {
  return <p>Loading...</p>;
}

if (error) {
  return <p>Error: {error}</p>;
}

return <UserList users={users} />;
```

A fourth useful state is:

```text
Empty
```

For example:

```jsx
if (users.length === 0) {
  return <p>No users found.</p>;
}
```

So a professional mental model is:

```text
Loading
   ↓
Success
   ├── Data
   └── Empty

or

Error
```

# 12. Fetching when a prop changes

Suppose:

```jsx
function UserProfile({ userId }) {
```

We want user data for the current `userId`.

```jsx
useEffect(() => {
  async function fetchUser() {
    const response = await fetch(
      `/api/users/${userId}`
    );

    const data = await response.json();

    setUser(data);
  }

  fetchUser();
}, [userId]);
```

Notice:

```jsx
[userId]
```

Now:

```text
userId = 10
↓
fetch user 10

userId changes to 20
↓
Effect runs again
↓
fetch user 20
```

This is one legitimate use of data fetching in an Effect: keeping displayed data synchronized with the current `userId`. ([React][1])

# 13. The race-condition problem

Now we reach one of the most important real-world problems.

Suppose:

```text
userId = 1
```

Request starts:

```text
Request A
```

Immediately user switches:

```text
userId = 2
```

Request starts:

```text
Request B
```

You expect:

```text
B finishes
→ User 2
```

But network requests don't necessarily finish in order.

Maybe:

```text
Request B finishes
↓
show User 2

Request A finishes later
↓
show User 1
```

Wrong user.

This is called a:

> **Race condition**

React's documentation specifically warns about this when fetching inside Effects. ([React][1])

---

# 14. React's documented `ignore` pattern

React demonstrates a cleanup approach like this:

```jsx
useEffect(() => {
  let ignore = false;

  async function fetchUser() {
    const response = await fetch(
      `/api/users/${userId}`
    );

    const data = await response.json();

    if (!ignore) {
      setUser(data);
    }
  }

  fetchUser();

  return () => {
    ignore = true;
  };
}, [userId]);
```

Now:

```text
Request user 1
      ↓
userId changes
      ↓
cleanup
ignore = true
      ↓
Request user 1 returns later
      ↓
ignored
```

So an obsolete request cannot update state. ([React][2])

# 15. Another modern option: `AbortController`

With the browser's `fetch()` API, you can also cancel an obsolete request.

Example:

```jsx
useEffect(() => {
  const controller = new AbortController();

  async function fetchUser() {
    try {
      setLoading(true);
      setError(null);

      const response = await fetch(
        `/api/users/${userId}`,
        {
          signal: controller.signal
        }
      );

      if (!response.ok) {
        throw new Error(
          `HTTP error: ${response.status}`
        );
      }

      const data = await response.json();

      setUser(data);
    } catch (error) {
      if (error.name !== "AbortError") {
        setError(error.message);
      }
    } finally {
      if (!controller.signal.aborted) {
        setLoading(false);
      }
    }
  }

  fetchUser();

  return () => {
    controller.abort();
  };
}, [userId]);
```

Now cleanup:

```jsx
controller.abort();
```

cancels the obsolete request.

---

# 16. `ignore` vs `AbortController`

They solve related but slightly different problems.

### Ignore pattern

```text
Request continues
↓
response arrives
↓
application ignores obsolete result
```

### AbortController

```text
Request becomes obsolete
↓
abort request
↓
stop it when possible
```

React's docs explicitly say cleanup for fetching should either **abort the fetch or ignore its result**. ([React][3])

For learning, understand both.

# 17. A robust `useEffect` fetch example

Here is a strong pattern:

```jsx
import {
  useEffect,
  useState
} from "react";

function UserProfile({ userId }) {
  const [user, setUser] = useState(null);
  const [loading, setLoading] =
    useState(true);
  const [error, setError] =
    useState(null);

  useEffect(() => {
    const controller =
      new AbortController();

    async function loadUser() {
      try {
        setLoading(true);
        setError(null);

        const response = await fetch(
          `/api/users/${userId}`,
          {
            signal: controller.signal
          }
        );

        if (!response.ok) {
          throw new Error(
            `Failed to load user: ${response.status}`
          );
        }

        const data =
          await response.json();

        setUser(data);
      } catch (error) {
        if (error.name !== "AbortError") {
          setError(error.message);
        }
      } finally {
        if (!controller.signal.aborted) {
          setLoading(false);
        }
      }
    }

    loadUser();

    return () => {
      controller.abort();
    };
  }, [userId]);

  if (loading) {
    return <p>Loading user...</p>;
  }

  if (error) {
    return (
      <p>
        Something went wrong: {error}
      </p>
    );
  }

  if (!user) {
    return <p>User not found.</p>;
  }

  return (
    <article>
      <h2>{user.name}</h2>
      <p>{user.email}</p>
    </article>
  );
}
```

This contains almost everything you should understand:

```text
useEffect
async/await
Loading
HTTP errors
Network errors
Cleanup
AbortController
Dependencies
Conditional rendering
```

# 18. Different kinds of errors

When fetching, don't think of all errors as identical.

You may have:

### Network error

```text
No internet
DNS problem
Server unavailable
Connection lost
```

`fetch()` may reject.

---

### HTTP error

```text
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
500 Server Error
```

You need:

```jsx
if (!response.ok) {
  throw new Error(...);
}
```

---

### JSON parsing error

This can fail:

```jsx
await response.json();
```

if the response isn't valid JSON.

Your `catch` block handles it.

---

### Application/business error

The API might return:

```json
{
  "success": false,
  "message": "User account disabled"
}
```

even though the HTTP request itself succeeded.

You may need:

```jsx
if (!data.success) {
  throw new Error(data.message);
}
```

So error handling has layers.

---

# 19. Don't show raw technical errors to users blindly

This:

```jsx
<p>{error.message}</p>
```

is useful during development.

But production users may not need:

```text
Failed to fetch
HTTP 502
Unexpected token at position...
```

Instead:

```jsx
<p>
  We couldn't load the users.
  Please try again.
</p>
```

while separately logging technical information.

# 20. Adding a Retry button

A useful error experience is:

```text
Request fails
↓
Show error
↓
Retry
```

One simple implementation:

```jsx
const [retryCount, setRetryCount] =
  useState(0);
```

Effect:

```jsx
useEffect(() => {
  async function fetchUsers() {
    // fetch...
  }

  fetchUsers();
}, [retryCount]);
```

Button:

```jsx
<button
  onClick={() =>
    setRetryCount(prev => prev + 1)
  }
>
  Retry
</button>
```

Now clicking Retry changes a dependency and starts a new request.

For larger applications, data-fetching libraries handle retry logic much better.

# 21. Fetching on user action is different

Suppose the user clicks:

```text
Save User
```

You don't usually need:

```jsx
useEffect(...)
```

for that.

Do:

```jsx
async function handleSave() {
  try {
    const response = await fetch(
      "/api/users",
      {
        method: "POST",
        headers: {
          "Content-Type":
            "application/json"
        },
        body: JSON.stringify(form)
      }
    );

    if (!response.ok) {
      throw new Error(
        "Unable to save user"
      );
    }

    const data = await response.json();

    console.log(data);
  } catch (error) {
    console.error(error);
  }
}
```

Then:

```jsx
<button onClick={handleSave}>
  Save
</button>
```

Why?

Because:

```text
User clicked Save
```

is the reason for the request.

That's an event handler, not an Effect.

A good example:

```text
Component says:
"While userId is 10, keep me synchronized
with user 10's server data."
```

Effect:

```jsx
useEffect(() => {
  // fetch userId
```

Good.

But:

```text
User clicked "Create Account"
```

should usually be:

```text
Event handler
```

not Effect.

# 23. "Old" vs "new" code syntax

A simplified comparison:

### Older/common Promise style

```jsx
useEffect(() => {
  fetch(url)
    .then(res => {
      if (!res.ok) {
        throw new Error("Failed");
      }

      return res.json();
    })
    .then(data => {
      setData(data);
    })
    .catch(error => {
      setError(error.message);
    });
}, []);
```

### Modern readable Effect style

```jsx
useEffect(() => {
  async function loadData() {
    try {
      const response =
        await fetch(url);

      if (!response.ok) {
        throw new Error("Failed");
      }

      const data =
        await response.json();

      setData(data);
    } catch (error) {
      setError(error.message);
    }
  }

  loadData();
}, []);
```

There is nothing inherently obsolete about Promises and `.then()`. `async/await` is still built on Promises.

The improvement is mainly:

```text
Readability
Structured error handling
Easier sequential code
```

# 24. But the truly modern architecture is bigger than syntax

This is the most important "old vs new" distinction.

Older React tutorials often teach:

```text
Component mounts
↓
useEffect
↓
fetch
↓
useState
```

for almost every API request.

That still works.

But React's current guidance says fetching directly in Effects has important disadvantages:

```text
No built-in caching
Race-condition boilerplate
Network waterfalls
No request deduplication
Loading-state repetition
Harder server rendering
Repeated fetching
```

React recommends using a framework's built-in data fetching when you have one, or considering client-side caching/data libraries when working without such a framework. ([React][1])

# 26. Custom Hook as the next step

Once you understand data fetching, you can extract it.

For example:

```jsx
function useUsers() {

    useState([]);

  const [loading, setLoading] =
    useState(true);

  const [error, setError] =
    useState(null);

        const response = await fetch(
          "/api/users",

              controller.signal
          }

          throw new Error(
            "Failed to load users"
          );

          await response.json();

        if (
          error.name !== "AbortError"

          setLoading(false);
        }
```

```jsx
function Users() {

```

Now fetching logic and UI are separated.

# 27. Common beginner mistakes

### Mistake 1: async Effect callback

Avoid:

```jsx
useEffect(async () => {
  // ...
}, []);
```

Use:

```jsx
useEffect(() => {
  async function fetchData() {
    // ...
  }

  fetchData();
}, []);
```

---

### Mistake 2: no `response.ok`

Weak:

```jsx
const response = await fetch(url);
const data = await response.json();
```

Better:

```jsx
const response = await fetch(url);

if (!response.ok) {
  throw new Error(
    `HTTP ${response.status}`
  );
}

const data = await response.json();
```

---

### Mistake 3: no error state

Avoid assuming every request succeeds.

Use:

```jsx
const [error, setError] =
  useState(null);
```

---

### Mistake 4: no loading state

Without:

```jsx
loading
```

the user may see an empty UI and not know whether:

```text
There is no data
or
Data is still loading
```

---

### Mistake 5: no cleanup

Especially when dependencies change:

```jsx
useEffect(() => {
  fetch(`/api/users/${userId}`);
}, [userId]);
```

consider stale responses/race conditions. React recommends aborting or ignoring obsolete fetch results. ([React][3])

---

### Mistake 6: fetching in an Effect when a button caused it

Avoid creating unnecessary state just to trigger an Effect.

If:

```text
Click button
→ API request
```

put the request in the event handler.

---

### Mistake 7: infinite fetching

Bad:

```jsx
useEffect(() => {
  fetchUsers().then(data => {
    setUsers(data);
  });
});
```

No dependency array.

This Effect runs after every render.

Then:

```text
Effect
↓
setUsers
↓
render
↓
Effect
↓
setUsers
↓
...
```

Use the correct dependency array.

# Common interview questions

### 1. How do you fetch data using `useEffect`?

> Create state for the data and request status, then start the asynchronous request inside the Effect. Handle success and errors, and add cleanup if the request can become obsolete.

---

### 2. Can `useEffect` itself be async?

No.

> The Effect callback must return either nothing or a cleanup function. Since an async function returns a Promise, define an async function inside the Effect and call it.

---

### 3. How do you handle errors with `fetch()`?

Use:

```jsx
try {
  const response = await fetch(url);

  if (!response.ok) {
    throw new Error(
      `HTTP error ${response.status}`
    );
  }
} catch (error) {
  // handle error
}
```

---

### 4. Why check `response.ok`?

> Because `fetch()` does not automatically reject every HTTP error response such as 404 or 500.

---

### 5. What is a race condition in data fetching?

> A race condition occurs when multiple requests are running and an older request finishes after a newer request, potentially overwriting the newer data.

---

### 6. How can you prevent race conditions?

Possible strategies include:

```text
Ignore stale responses
Abort obsolete requests
Use a data-fetching/cache library
```

React's documentation demonstrates ignoring stale results and recommends cleanup for Effect-based fetching. ([React][2])

---

### 7. What is `AbortController`?

> A browser API that can provide an abort signal to `fetch()` so an obsolete request can be cancelled.

---

### 8. What are the common states of a fetch request?

```text
Loading
Success
Error
Empty
```

---

### 9. Should all API requests be inside `useEffect`?

No.

> Requests caused by a specific user action normally belong in that event handler. Effects are useful when fetching is needed to synchronize the component with changing external data.

---

### 10. Is fetching inside `useEffect` still valid?

Yes.

But direct Effect fetching is low-level and requires you to handle concerns such as race conditions, caching, and loading/error states yourself. React recommends framework data-loading mechanisms or client-side caching solutions for larger applications when available. ([React][1])

# The mental model to remember

For simple Effect-based fetching:

```text
Component Render
      ↓
useEffect
      ↓
Set loading = true
      ↓
fetch()
      ↓
      ├── Success
      │      ↓
      │   response.ok?
      │      ↓
      │   JSON data
      │      ↓
      │   setData()
      │
      └── Failure
             ↓
          catch()
             ↓
          setError()

      ↓
finally()
      ↓
loading = false
```

For dependencies:

```text
userId changes
      ↓
cleanup old request
      ↓
start new request
      ↓
only current request
updates the UI
```

For your learning progression, I would master these in this exact order:

```text
1. fetch()
2. Promise + .then()
3. async / await
4. try / catch / finally
5. response.ok
6. loading / error / data state
7. useEffect dependencies
8. race conditions
9. cleanup
10. AbortController
11. Custom fetching Hook
12. Later: TanStack Query / framework data fetching
```

If you understand steps **1–10**, you understand manual React data fetching well enough to start building real API-driven React projects.
