When someone says **“ways of using React.js”**, they may be talking about two things:

1. **How React can be added/setup in a project**
2. **What kind of application architecture React can be used for**

You should understand both.

React is designed for gradual adoption—you can use React for one small part of an existing page or let React control an entire application. ([React][1])

---

# 1. Use React in an Online Sandbox

The easiest way to experiment with React is without installing anything.

Examples include:

```text
React documentation sandbox
CodeSandbox
StackBlitz
CodePen
```

You can write something like:

```jsx
function App() {
  return <h1>Hello React</h1>;
}
```

This method is useful for:

```text
Learning React
Testing components
Trying an idea
Sharing small examples
Interview practice
```

It is **not normally how you would build a serious production application**.

The official React documentation explicitly supports browser-based sandboxes for learning and experimentation. ([React][2])

---

# 2. Build a React SPA with Vite

This is one of the most important methods for you to learn.

SPA means:

> **Single Page Application**

A React SPA commonly has one initial HTML document, while React manages the application's UI and client-side interactions.

For learning React from scratch, Vite is an excellent environment.

You can create a project with:

```bash
npm create vite@latest
```

Then choose:

```text
React
```

or:

```text
React + TypeScript
```

Vite currently provides official React templates. ([vitejs][3])

A typical project looks like:

```text
my-app/
│
├── src/
│   ├── App.jsx
│   ├── main.jsx
│   ├── components/
│   └── assets/
│
├── index.html
├── package.json
└── vite.config.js
```

Your `main.jsx` might contain:

```jsx
import { createRoot } from "react-dom/client";
import App from "./App.jsx";

createRoot(document.getElementById("root")).render(
  <App />
);
```

And your HTML contains:

```html
<div id="root"></div>
```

React then controls everything inside:

```html
<div id="root"></div>
```

The official React API describes `createRoot()` as the mechanism for displaying React components inside a browser DOM node. ([React][4])

# 3. Use React for Only Part of an Existing Website

This is extremely important because:

> **Using React does not mean rebuilding the whole website in React.**

Suppose you already have:

```text
WordPress website
Laravel website
Django website
PHP website
Existing HTML website
```

You could keep the existing website and use React only for an interactive section.

Imagine:

```html
<header>
  Existing website header
</header>

<main>
  Existing website content

  <div id="calculator"></div>

  Existing website content
</main>

<footer>
  Existing footer
</footer>
```

React can control only:

```html
<div id="calculator"></div>
```

For example:

```jsx
import { createRoot } from "react-dom/client";
import Calculator from "./Calculator";

const container = document.getElementById("calculator");

createRoot(container).render(
  <Calculator />
);
```

Now:

```text
Traditional website
      ↓
-------------------
Header
Content
-------------------
React Calculator
-------------------
Content
Footer
-------------------
```

Only the calculator is React.

The React documentation explicitly describes this as a common integration strategy for existing websites. ([React][1])

This could be very useful with your WordPress background.

For example:

```text
WordPress
    +
React
```

You might build:

```text
Mortgage calculator
Advanced search
Booking interface
Product configurator
Dashboard
Interactive filter
Complex form
Analytics widget
```

using React while WordPress continues handling the rest of the site.

# 4. Use React for an Entire Frontend

Instead of one small React section, React can control your entire frontend.

For example:

```text
index.html
    ↓
#root
    ↓
<App />
    ↓
Entire Application
```

Your application may look like:

```text
App
├── Navbar
├── Sidebar
├── Dashboard
│   ├── Stats
│   ├── Chart
│   └── Orders
└── Footer
```

Everything becomes React components:

```jsx
function App() {
  return (
    <>
      <Navbar />
      <Sidebar />
      <Dashboard />
      <Footer />
    </>
  );
}
```

This is common for things like:

```text
Admin dashboards
CRM systems
SaaS applications
Internal tools
Project management apps
Booking apps
Complex portals
```

# 5. React as a Frontend + Separate Backend

This is a very common professional architecture.

Suppose you have:

```text
React
   ↓
REST API
   ↓
Backend
   ↓
Database
```

The backend could be:

```text
Node.js
PHP
Laravel
Django
Ruby on Rails
.NET
Java
WordPress
```

React doesn't care much what backend technology you use.

For example:

```jsx
fetch("https://example.com/api/products")
  .then(response => response.json())
  .then(data => console.log(data));
```

Architecture:

```text
              HTTP/API
React Frontend ───────────> Backend
                              ↓
                           Database
```

For example:

```text
React
   ↓
Node.js / Express
   ↓
PostgreSQL
```

Or:

```text
React
   ↓
WordPress REST API
   ↓
WordPress / MySQL
```

The second architecture is particularly relevant if you're working with WordPress.

It is often called:

> **Headless WordPress**

# 6. React + Headless CMS

Instead of WordPress generating the frontend HTML, WordPress can become primarily a content management/backend system.

Traditional WordPress:

```text
WordPress
   ↓
PHP Theme
   ↓
HTML
   ↓
Browser
```

Headless WordPress:

```text
WordPress
    ↓
REST API / GraphQL
    ↓
React / Next.js
    ↓
Browser
```

For example, WordPress stores:

```text
Posts
Pages
Authors
Images
Custom Post Types
ACF fields
```

React retrieves that data and creates the UI.

Example:

```jsx
async function getPosts() {
  const response = await fetch(
    "https://example.com/wp-json/wp/v2/posts"
  );

  return response.json();
}
```

This combination can be valuable when you want:

```text
WordPress CMS experience
+
Modern React frontend
```

# 7. Use React Through a Framework

This is increasingly important for production applications.

React's current documentation recommends starting new React applications with a framework when appropriate. ([React][5])

One major example is:

```text
Next.js
```

Think about the relationship like this:

```text
JavaScript
    ↓
React
    ↓
Next.js
```

React gives you:

```text
Components
Props
State
Hooks
Rendering
```

A React framework can additionally provide things like:

```text
Routing
Server rendering
Data loading
Build optimization
Server functionality
Static generation
Deployment patterns
```

Instead of manually building all infrastructure around React, a framework gives you an application structure.

# 8. Client-Side Rendering — CSR

This is another important way React can be delivered.

CSR means:

> **Client-Side Rendering**

Suppose the browser requests:

```text
example.com/dashboard
```

The browser might initially receive something like:

```html
<div id="root"></div>

<script src="app.js"></script>
```

Then JavaScript executes:

```text
Browser receives HTML
        ↓
Downloads JavaScript
        ↓
React starts
        ↓
React renders application
        ↓
User sees UI
```

Conceptually:

```text
Server
  ↓
Basic HTML + JavaScript
  ↓
Browser
  ↓
React rendering
```

A Vite-based SPA commonly uses this model.

---

# 9. Server-Side Rendering — SSR

SSR means:

> **Server-Side Rendering**

Instead of sending nearly empty application HTML initially, the server generates HTML from React.

Conceptually:

```text
Browser Request
      ↓
Server
      ↓
React renders HTML
      ↓
HTML sent to browser
      ↓
Browser displays content
      ↓
JavaScript loads
      ↓
React hydrates the page
```

For example, the browser could immediately receive:

```html
<h1>Our Products</h1>

<div>
  <h2>MacBook Pro</h2>
  <p>$1999</p>
</div>
```

rather than waiting for client JavaScript to construct all visible content.

React documentation recommends frameworks for this kind of optimization rather than manually implementing the entire infrastructure yourself. ([React][4])

---

# 10. What is Hydration?

If the server already generated:

```html
<h1>Hello Kawshar</h1>
<button>Click Me</button>
```

React shouldn't destroy it and create everything again.

Instead, React attaches its behavior to the existing server-rendered HTML.

This process is called:

> **Hydration**

Conceptually:

```text
Server-generated HTML
        +
React JavaScript
        ↓
    Hydration
        ↓
Interactive React application
```

For server-rendered HTML, React uses:

```jsx
hydrateRoot(...)
```

instead of:

```jsx
createRoot(...)
```

The official React documentation makes this distinction explicitly. ([React][4])

---

# 11. Static Site Generation — SSG

Another approach is:

> **Static Site Generation**

Instead of generating a page for every request:

```text
Request
  ↓
Server generates HTML
```

the HTML can be generated ahead of time:

```text
Build time
   ↓
Generate HTML files
   ↓
Deploy
   ↓
Serve static HTML
```

Good examples include:

```text
Marketing websites
Blogs
Documentation sites
Portfolio sites
Landing pages
```

A React framework can support this.

React's current documentation notes that modern React frameworks can support CSR, SPA architectures, static generation, and server rendering depending on project requirements. ([React][5])

# 12. React as a Full-Stack Application

Developers sometimes think:

```text
React = Frontend only
```

React itself is primarily concerned with UI, but modern React frameworks can be used in a full-stack architecture.

For example:

```text
Browser
   ↓
Next.js / React
   ↓
Server logic
   ↓
Database
```

You could have:

```text
React Components
Server Components
API endpoints
Authentication
Database
Payments
```

in the wider React application architecture.

This is one reason learning React properly before Next.js is important.

# 14. React With JSX

This is the normal way you will write React:

```jsx
function App() {
  return (
    <div>
      <h1>Hello React</h1>
    </div>
  );
}
```

This is:

```text
React + JSX
```

JSX makes UI easier to read and write.

# 15. React Without JSX

React technically doesn't require JSX.

This:

```jsx
<h1>Hello</h1>
```

can conceptually be created with APIs such as:

```js
createElement("h1", null, "Hello");
```

So:

```text
JSX
↓
transformed into
↓
JavaScript representation/instructions
```

You normally **should use JSX**.

But this distinction matters for understanding:

> JSX and React are not the same thing.

React is the library.

JSX is syntax commonly used with React.

# 16. Multiple React Roots

React doesn't require exactly one React root on an entire HTML document.

Suppose an old website has:

```html
<header>
  Existing Navigation
</header>

<div id="product-filter"></div>

<article>
  Existing Content
</article>

<div id="comments"></div>
```

You could create:

```jsx
createRoot(
  document.getElementById("product-filter")
).render(<ProductFilter />);
```

and separately:

```jsx
createRoot(
  document.getElementById("comments")
).render(<Comments />);
```

Now:

```text
Existing Website

├── Traditional Header
├── React Product Filter
├── Traditional Content
├── React Comments
└── Traditional Footer
```

React officially supports rendering different React roots into different DOM nodes on partially React-powered pages. ([React][4])

This is an excellent example of React's gradual adoption model.

Think of it like this:

| Requirement                | Good approach                   |
| -------------------------- | ------------------------------- |
| Just learning React        | Vite                            |
| Small React experiment     | Online sandbox                  |
| Add one interactive widget | React inside existing site      |

| SaaS application           | React framework                 |

# One Important Current Change: Create React App

You will see many old tutorials saying:

```bash
npx create-react-app my-app
```

You should know this because it frequently appears in courses and interview material.

However:

> **Create React App has been deprecated.**

React's current documentation explicitly says not to use Create React App for new projects. ([React][2])

For learning basic client-side React, I would instead teach you using:

```text
Vite + React
```

```text
Next.js
```

## Common Interview Questions

**Q: Can React be added to an existing website?**

Yes. React is designed for gradual adoption. You can render one or more React components into specific DOM nodes without rebuilding the entire site. ([React][1])

**Q: Does React require JSX?**

No. JSX is the normal and recommended way to write React UI, but React can be used without JSX.

**Q: What is the difference between CSR and SSR?**

CSR generates much of the UI in the browser after JavaScript loads. SSR generates initial HTML on the server and sends it to the browser.

**Q: What is hydration?**

Hydration is the process where React attaches interactive behavior to HTML that was already rendered on the server.

**Q: Can React be used with WordPress?**

Yes. You can add React components to an existing WordPress site or use WordPress as a headless CMS and build the frontend with React/Next.js.

**Q: Should we use Create React App today?**

No. Create React App is deprecated. React's current guidance favors frameworks for new production apps, while Vite is a strong option for learning React fundamentals or building a client-side app from scratch. ([React][2])

### The most important distinction

Don't confuse:

```text
"How do I install React?"
```

with:

```text
"How is my React application rendered?"
```

For example:

```text
Vite
= development/build tooling

React
= UI library

CSR
= rendering strategy

SSR
= rendering strategy

SSG
= generation strategy

Next.js
= React framework

ReactDOM
= React's DOM renderer
```

Understanding those differences will prevent a lot of confusion when you move from basic React into Next.js.
