Sharing state between sibling components in React usually means:

> **Move the shared state up to their nearest common parent, then pass the state and updater functions down through props.**

This pattern is called:

> **Lifting state up**

## 1. The problem

Imagine this structure:

```text
App
├── InputBox
└── DisplayName
```

`InputBox` needs to change a name.

`DisplayName` needs to show that same name.

These are sibling components because they have the same parent.

```text
          App
         /   \
        /     \
InputBox     DisplayName
```

The problem is:

```text
InputBox has data
DisplayName needs that data
```

Sibling components should not normally try to directly access each other's state.

Instead:

```text
InputBox
     ↑
     │
    App
     │
     ↓
DisplayName
```

The parent becomes the shared source of truth.

---

# 2. Wrong mental model

You may initially try this:

```jsx
function InputBox() {
  const [name, setName] = useState("");

  return (
    <input
      value={name}
      onChange={e => setName(e.target.value)}
    />
  );
}
```

Then:

```jsx
function DisplayName() {
  return <h2>{name}</h2>;
}
```

This doesn't work.

Why?

Because:

```text
name
```

belongs to `InputBox`.

`DisplayName` has no access to it.

State is local to the component that owns it.

---

# 3. Correct solution: lift the state up

Move:

```jsx
const [name, setName] = useState("");
```

to the parent:

```jsx
function App() {
  const [name, setName] = useState("");

  return (
    <>
      <InputBox
        name={name}
        setName={setName}
      />

      <DisplayName name={name} />
    </>
  );
}
```

Now both siblings can work with the same state.

---

# 4. Complete example

```jsx
import { useState } from "react";

function InputBox({ name, setName }) {
  return (
    <input
      type="text"
      value={name}
      onChange={e => setName(e.target.value)}
    />
  );
}

function DisplayName({ name }) {
  return (
    <h2>Hello {name}</h2>
  );
}

function App() {
  const [name, setName] = useState("");

  return (
    <div>
      <InputBox
        name={name}
        setName={setName}
      />

      <DisplayName name={name} />
    </div>
  );
}

export default App;
```

Now the flow is:

```text
User types in InputBox
        ↓
setName()
        ↓
App state changes
        ↓
App re-renders
        ↓
new name passed to both children
        ↓
DisplayName updates
```

This is the basic pattern you need to understand.

---

# 5. Who owns the state?

This is a very important React concept.

Initially:

```text
InputBox
owns name state
```

But now both:

```text
InputBox
DisplayName
```

need the same data.

So state moves to:

```text
App
```

because `App` is the nearest common parent.

Think:

```text
Who needs the state?
        ↓
Find nearest common parent
        ↓
Put state there
```

---

# 6. This is called a single source of truth

If both siblings had separate state:

```jsx
function InputBox() {
  const [name, setName] = useState("");
}
```

and:

```jsx
function DisplayName() {
  const [name, setName] = useState("");
}
```

you would have two different `name` states.

They are not connected.

```text
InputBox state
name = "John"

DisplayName state
name = ""
```

That creates synchronization problems.

Instead, keep one shared state:

```text
App
name = "John"
```

Then pass it down.

This is called:

> **Single source of truth**

---

# 7. Parent-to-child data flow

React mainly uses one-way data flow.

```text
Parent
  ↓ props
Child
```

In our example:

```text
App
 ↓
name
 ↓
InputBox
```

and:

```text
App
 ↓
name
 ↓
DisplayName
```

So data flows downward.

---

# 8. Child-to-parent communication

You may ask:

> How can `InputBox` update state that belongs to `App`?

The parent passes a function down.

Example:

```jsx
<InputBox setName={setName} />
```

Then child:

```jsx
function InputBox({ setName }) {
  return (
    <input
      onChange={e => setName(e.target.value)}
    />
  );
}
```

So:

```text
Parent owns state
       ↓
Parent passes setter
       ↓
Child calls setter
       ↓
Parent state updates
```

This is a fundamental React pattern.

---

# 9. Better pattern: pass a meaningful handler

You don't always need to pass the raw setter.

Instead of:

```jsx
<InputBox setName={setName} />
```

you can write:

```jsx
function App() {
  const [name, setName] = useState("");

  function handleNameChange(newName) {
    setName(newName);
  }

  return (
    <>
      <InputBox
        name={name}
        onNameChange={handleNameChange}
      />

      <DisplayName name={name} />
    </>
  );
}
```

Then:

```jsx
function InputBox({ name, onNameChange }) {
  return (
    <input
      value={name}
      onChange={e => onNameChange(e.target.value)}
    />
  );
}
```

This is often cleaner because:

```text
onNameChange
```

describes the intent better than:

```text
setName
```

# 10. Sibling example: Counter controls

Imagine:

```text
App
├── IncreaseButton
└── CounterDisplay
```

Code:

```jsx
import { useState } from "react";

function IncreaseButton({ onIncrease }) {
  return (
    <button onClick={onIncrease}>
      Increase
    </button>
  );
}

function CounterDisplay({ count }) {
  return (
    <h2>Count: {count}</h2>
  );
}

function App() {
  const [count, setCount] = useState(0);

  function handleIncrease() {
    setCount(prev => prev + 1);
  }

  return (
    <>
      <IncreaseButton
        onIncrease={handleIncrease}
      />

      <CounterDisplay count={count} />
    </>
  );
}
```

Flow:

```text
IncreaseButton
      ↓ click
handleIncrease()
      ↓
App count changes
      ↓
CounterDisplay gets new count
```

# 11. Another example: Search and results

This is a very realistic pattern.

```text
App
├── SearchInput
└── ProductList
```

`SearchInput` changes the search term.

`ProductList` uses the search term.

```jsx
import { useState } from "react";

function SearchInput({ search, onSearchChange }) {
  return (
    <input
      value={search}
      onChange={e =>
        onSearchChange(e.target.value)
      }
      placeholder="Search products"
    />
  );
}

function ProductList({ search }) {
  const products = [
    "Laptop",
    "Phone",
    "Tablet"
  ];

  const filteredProducts =
    products.filter(product =>
      product
        .toLowerCase()
        .includes(search.toLowerCase())
    );

  return (
    <ul>
      {filteredProducts.map(product => (
        <li key={product}>
          {product}
        </li>
      ))}
    </ul>
  );
}

function App() {
  const [search, setSearch] = useState("");

  return (
    <>
      <SearchInput
        search={search}
        onSearchChange={setSearch}
      />

      <ProductList search={search} />
    </>
  );
}
```

Now:

```text
User types "lap"
      ↓
search state in App
      ↓
ProductList receives "lap"
      ↓
filter()
      ↓
Laptop displayed
```

# 12. Another example: Temperature converter

This is a classic React example.

```text
TemperatureCalculator
├── CelsiusInput
└── FahrenheitDisplay
```

Code:

```jsx
import { useState } from "react";

function CelsiusInput({
  celsius,
  onChange
}) {
  return (
    <input
      type="number"
      value={celsius}
      onChange={e => onChange(e.target.value)}
    />
  );
}

function FahrenheitDisplay({ celsius }) {
  const fahrenheit =
    celsius === ""
      ? ""
      : (Number(celsius) * 9) / 5 + 32;

  return (
    <p>
      Fahrenheit: {fahrenheit}
    </p>
  );
}

function App() {
  const [celsius, setCelsius] = useState("");

  return (
    <>
      <CelsiusInput
        celsius={celsius}
        onChange={setCelsius}
      />

      <FahrenheitDisplay
        celsius={celsius}
      />
    </>
  );
}
```

Again:

```text
Shared state
↓
Parent
↓
Children receive it through props
```

# 13. Siblings do not share state directly

This is important.

Avoid this mental model:

```text
Sibling A
→ send state directly
→ Sibling B
```

React normally does:

```text
Sibling A
      ↑
   Parent
      ↓
Sibling B
```

The parent coordinates both.

---

# 14. Why does React work this way?

Because it makes data flow predictable.

You know:

```text
Where is the state?
→ Parent
```

You know:

```text
Who can change it?
→ Components given callback functions
```

You know:

```text
Who can read it?
→ Components given props
```

This reduces confusing synchronization bugs.

---

# 15. When should you lift state up?

Lift state when:

```text
Two or more components need the same data
```

or:

```text
One component changes data
Another component needs to react to that change
```

Examples:

```text
Search input + results
Form input + preview
Tabs + content
Cart button + cart summary
Filters + product list
Sidebar control + page layout
```

---

# 16. Do not lift state higher than necessary

Suppose:

```text
App
├── Dashboard
│   ├── Filter
│   └── ProductList
└── Footer
```

Only:

```text
Filter
ProductList
```

need `search`.

You do not necessarily need to store it in:

```text
App
```

You could store it in:

```text
Dashboard
```

because that is their nearest common parent.

Good:

```text
App
└── Dashboard
    ├── Filter
    └── ProductList
```

State:

```text
Dashboard
```

not automatically:

```text
App
```

A strong rule is:

> **Keep state as close as possible to the components that need it.**

---

# 17. Avoid duplicate state

Suppose:

```jsx
function App() {
  const [price, setPrice] = useState(100);
}
```

Then child A receives price.

Child B also needs price.

Do not create another:

```jsx
const [price, setPrice] = useState(100);
```

inside Child B.

Now you have:

```text
price A
price B
```

which can become inconsistent.

Use one shared state instead.

---

# 18. Derived data usually should not become another state

Suppose parent has:

```jsx
const [firstName, setFirstName] = useState("");
const [lastName, setLastName] = useState("");
```

Sibling component needs:

```text
full name
```

You don't necessarily need:

```jsx
const [fullName, setFullName] = useState("");
```

Instead:

```js
const fullName =
  `${firstName} ${lastName}`;
```

Then pass it:

```jsx
<NamePreview fullName={fullName} />
```

Remember:

> Store real state. Calculate derived values when possible.

---

# 19. Passing multiple handlers

Example:

```text
App
├── Controls
└── CounterDisplay
```

You can pass:

```jsx
function App() {
  const [count, setCount] = useState(0);

  function increase() {
    setCount(prev => prev + 1);
  }

  function decrease() {
    setCount(prev => prev - 1);
  }

  function reset() {
    setCount(0);
  }

  return (
    <>
      <Controls
        onIncrease={increase}
        onDecrease={decrease}
        onReset={reset}
      />

      <CounterDisplay count={count} />
    </>
  );
}
```

Child:

```jsx
function Controls({
  onIncrease,
  onDecrease,
  onReset
}) {
  return (
    <>
      <button onClick={onIncrease}>
        +
      </button>

      <button onClick={onDecrease}>
        -
      </button>

      <button onClick={onReset}>
        Reset
      </button>
    </>
  );
}
```

This is clean component communication.

```text

├── Header
├── Sidebar
```

```text
currentUser
```

# 23. Prop drilling

Suppose:

```text
App
↓
Layout
↓
Dashboard
↓
Sidebar
↓
Profile
```

and `App` has to pass:

```text
user
```

through every layer.

That is sometimes called:

> **Prop drilling**

For a few levels, it is often perfectly fine.

For deeply shared state, you may consider:

```text
Context
Redux
Zustand
```

later.

But for your current learning stage:

```text
Props + lifting state
```

is the correct foundation.

# 24. Common beginner mistake: state in both siblings

Bad:

```jsx
function SearchInput() {
  const [search, setSearch] = useState("");
}
```

and separately:

```jsx
function ProductList() {
  const [search, setSearch] = useState("");
}
```

These are two separate states.

Changing one does not change the other.

Better:

```jsx
function App() {
  const [search, setSearch] = useState("");
}
```

Then pass it to both.

---

# 25. Common beginner mistake: changing props directly

Suppose:

```jsx
function InputBox({ name }) {
  name = "John";
}
```

This is wrong conceptually.

Props are read-only inputs.

If the child needs to change something, use a callback:

```jsx
function InputBox({
  name,
  onNameChange
}) {
  return (
    <input
      value={name}
      onChange={e =>
        onNameChange(e.target.value)
      }
    />
  );
}
```

---

# 26. Common beginner mistake: lifting state too high

Suppose only:

```text
Modal
ModalButton
```

need:

```text
isOpen
```

Don't automatically put it in the root `App`.

Keep it in their common parent.

Example:

```text
App
└── ModalSection
    ├── ModalButton
    └── Modal
```

Store:

```text
isOpen
```

inside:

```text
ModalSection
```

This keeps state local and easier to manage.

# 27. A realistic cart example

Imagine:

```text
ShopPage
├── ProductList
└── CartSummary
```

`ProductList` adds products.

`CartSummary` shows cart count.

Shared state belongs in `ShopPage`.

```jsx
import { useState } from "react";

function ProductList({ onAdd }) {
  const products = [
    { id: 1, name: "Laptop" },
    { id: 2, name: "Phone" }
  ];

  return (
    <div>
      {products.map(product => (
        <div key={product.id}>
          <span>{product.name}</span>

          <button
            onClick={() => onAdd(product)}
          >
            Add to Cart
          </button>
        </div>
      ))}
    </div>
  );
}

function CartSummary({ cart }) {
  return (
    <h2>
      Cart Items: {cart.length}
    </h2>
  );
}

function ShopPage() {
  const [cart, setCart] = useState([]);

  function handleAdd(product) {
    setCart(prevCart => [
      ...prevCart,
      product
    ]);
  }

  return (
    <>
      <ProductList onAdd={handleAdd} />

      <CartSummary cart={cart} />
    </>
  );
}
```

Flow:

```text
ProductList
    ↓
handleAdd(product)
    ↓
ShopPage cart state
    ↓
CartSummary receives new cart
    ↓
UI updates
```

This is exactly how sibling communication works in real apps.

# Common Interview Questions

### 1. How do sibling components share state in React?

A strong answer:

> Sibling components usually share state by lifting the state to their nearest common parent. The parent passes the shared state and callback functions to the children through props.

---

### 2. What is lifting state up?

> Lifting state up means moving state from a child component to the nearest common parent so multiple components can share and coordinate that state.

---

### 3. Can sibling components directly access each other's state?

No.

> State belongs to the component that owns it. Siblings normally communicate through their parent.

---

### 4. What is a single source of truth?

> A single source of truth means keeping shared data in one authoritative state location rather than duplicating the same state in multiple components.

---

### 5. How does a child update parent state?

The parent passes a callback.

Example:

```jsx
<Child onChange={handleChange} />
```

Then:

```jsx
function Child({ onChange }) {
  return (
    <button
      onClick={() => onChange("new value")}
    >
      Change
    </button>
  );
}
```

---

### 6. Why not duplicate state in two siblings?

> Because the two copies can become inconsistent and must be manually synchronized.

---

### 7. Where should shared state be placed?

> In the nearest common ancestor of all components that need that state.

---

### 8. What is prop drilling?

> Prop drilling is passing props through multiple intermediate components just to reach deeply nested descendants.

---

### 9. When should you use Context instead of lifting state?

> Context can be useful when many distant components need the same data and passing props through many layers becomes inconvenient. For nearby siblings, lifting state is usually simpler.

---

### 10. What is one-way data flow?

> React data normally flows from parent to child through props. Children can request changes by calling callback functions provided by the parent.

---

# The mental model you should remember

Whenever two siblings need the same state, think:

```text
Sibling A needs state
Sibling B needs state
        ↓
Who is their common parent?
        ↓
Put state there
        ↓
Pass state down through props
        ↓
Pass update callbacks down
```

The most important diagram is:

```text
Sibling A
    ↓
callback
    ↓
  Parent
 shared state
    ↓
   props
    ↓
Sibling B
```

And the core React code pattern is:

```jsx
function Parent() {
  const [value, setValue] = useState("");

  return (
    <>
      <SiblingA
        value={value}
        onChange={setValue}
      />

      <SiblingB
        value={value}
      />
    </>
  );
}
```

If you understand this pattern, you understand **lifting state up**, **single source of truth**, **parent-child communication**, and the foundation of shared state in React.
