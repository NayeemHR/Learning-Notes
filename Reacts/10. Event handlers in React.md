Event handlers in React are functions that run when a user interacts with the UI.

Typical events include:

```text
Click
Change
Submit
Mouse movement
Keyboard input
Focus
Blur
```

The core idea is:

> **An event handler is a function you give to a React element so React can run it when a specific event happens.**

# 1. Basic click event

```jsx
function App() {
  function handleClick() {
    console.log("Button clicked");
  }

  return (
    <button onClick={handleClick}>
      Click Me
    </button>
  );
}
```

The important part is:

```jsx
onClick={handleClick}
```

This tells React:

```text
When this button is clicked
        ↓
Run handleClick
```

---

# 2. React event names use camelCase

In normal HTML, you may see:

```html
<button onclick="doSomething()">
  Click
</button>
```

In React:

```jsx
<button onClick={handleClick}>
  Click
</button>
```

Notice:

```text
HTML
onclick

React
onClick
```

React events use camelCase.

Examples:

```jsx
onClick
onChange
onSubmit
onMouseEnter
onMouseLeave
onKeyDown
onFocus
onBlur
```

---

# 3. Pass the function, do not call it

This is one of the most important beginner concepts.

Correct:

```jsx
<button onClick={handleClick}>
  Click
</button>
```

Wrong:

```jsx
<button onClick={handleClick()}>
  Click
</button>
```

Why?

This:

```jsx
handleClick
```

means:

> Give React the function.

This:

```jsx
handleClick()
```

means:

> Execute the function immediately.

So:

```text
onClick={handleClick}
         ↑
Pass function
```

not:

```text
onClick={handleClick()}
         ↑
Call now
```

---

# 4. Inline event handlers

You can also write:

```jsx
function App() {
  return (
    <button
      onClick={() => {
        console.log("Clicked");
      }}
    >
      Click Me
    </button>
  );
}
```

Or shorter:

```jsx
<button onClick={() => console.log("Clicked")}>
  Click
</button>
```

This is common for simple logic.

---

# 5. Named function vs inline function

Both are valid.

Named:

```jsx
function handleClick() {
  console.log("Clicked");
}

<button onClick={handleClick}>
  Click
</button>
```

Inline:

```jsx
<button onClick={() => console.log("Clicked")}>
  Click
</button>
```

Use a named function when the logic is:

```text
Long
Reusable
Complex
Easier to test/read separately
```

Use inline functions for small expressions.

# 6. Event handlers and state

Event handlers are very often used to update state.

Example:

```jsx
import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
  }

  return (
    <div>
      <p>{count}</p>

      <button onClick={handleClick}>
        Increase
      </button>
    </div>
  );
}
```

Flow:

```text
User clicks
   ↓
handleClick()
   ↓
setCount()
   ↓
State updates
   ↓
Component re-renders
   ↓
UI updates
```

This pattern is fundamental.

# 7. The event object

React passes an event object to your handler.

Example:

```jsx
function handleClick(event) {
  console.log(event);
}
```

Then:

```jsx
<button onClick={handleClick}>
  Click
</button>
```

You will often see:

```js
event
```

or:

```js
e
```

Example:

```jsx
function handleClick(e) {
  console.log(e);
}
```

Both are the same idea.

---

# 8. What information is inside the event object?

The event object contains information about what happened.

For example:

```jsx
function handleClick(e) {
  console.log(e.target);
}
```

You may get the clicked button.

Useful properties include:

```text
e.target
e.currentTarget
e.type
e.key
```

And useful methods include:

```text
e.preventDefault()
e.stopPropagation()
```

---

# 9. `target` vs `currentTarget`

This is an important distinction.

Suppose:

```jsx
function App() {
  function handleClick(e) {
    console.log("target:", e.target);
    console.log("currentTarget:", e.currentTarget);
  }

  return (
    <button onClick={handleClick}>
      <span>Click Me</span>
    </button>
  );
}
```

If you click the `<span>`:

```text
e.target
→ span
```

because that is the exact element where the event originated.

But:

```text
e.currentTarget
→ button
```

because the event handler is attached to the button.

Remember:

```text
target
=
where event started

currentTarget
=
element whose handler is currently running
```

---

# 10. Passing arguments to event handlers

Suppose you need to delete a specific product.

You may have:

```jsx
function deleteProduct(id) {
  console.log(id);
}
```

You cannot write:

```jsx
<button onClick={deleteProduct(product.id)}>
  Delete
</button>
```

because that calls it during render.

Instead:

```jsx
<button
  onClick={() => deleteProduct(product.id)}
>
  Delete
</button>
```

The arrow function delays execution until the click happens.

Flow:

```text
User clicks
   ↓
Arrow function runs
   ↓
deleteProduct(product.id)
```

---

# 11. Passing both event and custom arguments

You can do:

```jsx
function handleDelete(id, e) {
  console.log(id);
  console.log(e);
}
```

Then:

```jsx
<button
  onClick={(e) => handleDelete(product.id, e)}
>
  Delete
</button>
```

Now you have both:

```text
product.id
+
event object
```

# 12. Input `onChange`

For form inputs, `onChange` is extremely common.

Example:

```jsx
import { useState } from "react";

function App() {
  const [name, setName] = useState("");

  function handleChange(e) {
    setName(e.target.value);
  }

  return (
    <div>
      <input
        type="text"
        value={name}
        onChange={handleChange}
      />

      <p>{name}</p>
    </div>
  );
}
```

When the user types:

```text
Input changes
   ↓
onChange
   ↓
handleChange(e)
   ↓
e.target.value
   ↓
setName()
   ↓
Component re-renders
```

This is the basic controlled input pattern.

---

# 13. Why `e.target.value`?

Suppose the user types:

```text
John
```

Then:

```js
e.target
```

is the input.

And:

```js
e.target.value
```

is:

```text
John
```

So:

```jsx
setName(e.target.value);
```

stores what the user typed.

# 14. Form `onSubmit`

Example:

```jsx
function LoginForm() {
  function handleSubmit(e) {
    e.preventDefault();

    console.log("Form submitted");
  }

  return (
    <form onSubmit={handleSubmit}>
      <input type="email" />

      <button type="submit">
        Login
      </button>
    </form>
  );
}
```

Important:

```js
e.preventDefault();
```

prevents the browser's normal form submission behavior, which would usually refresh or navigate the page.

---

# 15. Why use `onSubmit` on the form?

Do this:

```jsx
<form onSubmit={handleSubmit}>
```

instead of putting all submission logic only on:

```jsx
<button onClick={handleSubmit}>
```

Why?

Because a form can be submitted by:

```text
Clicking submit button
Pressing Enter
Browser accessibility behavior
```

So the semantic React pattern is:

```jsx
<form onSubmit={handleSubmit}>
```

# 19. Event bubbling

Events can move upward through the component's DOM structure.

Example:

```jsx
function App() {
  function handleParentClick() {
    console.log("Parent clicked");
  }

  function handleButtonClick() {
    console.log("Button clicked");
  }

  return (
    <div onClick={handleParentClick}>
      <button onClick={handleButtonClick}>
        Click Me
      </button>
    </div>
  );
}
```

Clicking the button may log:

```text
Button clicked
Parent clicked
```

Why?

Because the click event bubbles upward.

Conceptually:

```text
button
  ↓
parent div
  ↓
higher ancestors
```

---

# 20. `stopPropagation()`

If you don't want the event to bubble:

```jsx
function handleButtonClick(e) {
  e.stopPropagation();

  console.log("Button clicked");
}
```

Now:

```jsx
<button onClick={handleButtonClick}>
```

may prevent the parent click handler from running for that event.

Use this carefully.

Do not automatically stop propagation everywhere.

---

# 21. `preventDefault()` vs `stopPropagation()`

Very common interview question.

```js
e.preventDefault()
```

means:

> Prevent the browser's default behavior.

Example:

```text
Prevent form submission/navigation
```

While:

```js
e.stopPropagation()
```

means:

> Stop the event from moving through parent elements.

Remember:

```text
preventDefault
→ browser behavior

stopPropagation
→ event propagation
```

# 23. Custom event prop names

For your own components, the prop does not technically need to be named `onClick`.

Example:

```jsx
function ProductCard({ onDeleteProduct }) {

      Delete
    </button>

```

Parent:

```jsx
<ProductCard
  onDeleteProduct={handleDelete}

```

For custom component callback props, names often start with:

```text
on
```

Examples:

```jsx
onDelete
onSave

```

This makes intent clear.

The function itself is commonly named:

```text
handle + Event
```

Examples:

```js

```


# 26. Event handler + state + array

A more realistic example:

```jsx
import { useState } from "react";

function App() {
  const [products, setProducts] = useState([
    { id: 1, name: "Laptop" },
    { id: 2, name: "Phone" }
  ]);

  function handleDelete(id) {
    setProducts(
      products.filter(product => product.id !== id)
    );
  }

  return (
    <div>
      {products.map(product => (
        <div key={product.id}>
          <span>{product.name}</span>

          <button
            onClick={() => handleDelete(product.id)}
          >
            Delete
          </button>
        </div>
      ))}
    </div>
  );
}
```

The complete flow:

```text
User clicks Delete
      ↓
Arrow function runs
      ↓
handleDelete(product.id)
      ↓
filter()
      ↓
new products array
      ↓
setProducts()
      ↓
component rerenders
      ↓
deleted product disappears
```

This is a core real-world React pattern.

# 28. Toggling state

Very common:

```jsx
const [open, setOpen] = useState(false);

function handleToggle() {
  setOpen(!open);
}
```

Better when based on previous state:

```jsx
function handleToggle() {
  setOpen(prevOpen => !prevOpen);
}
```

Why?

Because the new state depends on the previous state.

This pattern is safer:

```jsx
setOpen(prev => !prev);
```

---

# 29. Updating counters correctly

You may write:

```jsx
setCount(count + 1);
```

Usually fine.

But if you perform multiple updates:

```jsx
setCount(count + 1);
setCount(count + 1);
```

you may not get the result you expect.

Use the functional updater:

```jsx
setCount(prevCount => prevCount + 1);
setCount(prevCount => prevCount + 1);
```

This is especially important when the new value depends on the previous value.

---

# 30. React batches state updates

Suppose:

```jsx
function handleClick() {
  setCount(prev => prev + 1);
  setOpen(true);
  setName("John");
}
```

React can batch these state updates together to avoid unnecessary renders.

Conceptually:

```text
Event handler starts
      ↓
Several state updates
      ↓
React batches updates
      ↓
Rerender
```

You do not normally need to manually manage this.

---

# 31. Do not mutate state inside event handlers

Bad:

```jsx
function handleAdd() {
  products.push(newProduct);
}
```

If `products` is React state, this mutates the existing array.

Prefer:

```jsx
function handleAdd() {
  setProducts([
    ...products,
    newProduct
  ]);
}
```

Same with objects.

Avoid:

```js
user.name = "John";
```

Prefer:

```js
setUser({
  ...user,
  name: "John"
});
```

# 32. Side effects belong naturally in event handlers sometimes

Suppose a user clicks:

```jsx
<button onClick={handleDownload}>
  Download
</button>
```

The handler can perform an action caused directly by the user.

Examples:

```text
Send request
Save data
Download file
Open dialog
Copy text
Navigate
```

React's purity requirement applies mainly to rendering.

Event handlers are exactly where many intentional side effects belong.

---

# 33. Render logic vs event logic

Bad:

```jsx
function App() {
  alert("Hello");

  return <button>Click</button>;
}
```

This runs during rendering.

Better:

```jsx
function App() {
  function handleClick() {
    alert("Hello");
  }

  return (
    <button onClick={handleClick}>
      Click
    </button>
  );
}
```

Now the side effect happens because of the user action.

---

# 34. Event handlers are not effects

Do not confuse:

```text
Event handler
```

with:

```text
useEffect
```

Use an event handler when something happens because the user explicitly did something.

Example:

```text
User clicked Save
→ event handler
```

Use `useEffect` when the component needs to synchronize with an external system because of rendering/state changes.

Example:

```text
userId changed
→ synchronize external subscription
```

A useful rule:

> If something should happen because the user clicked something, it usually belongs in the event handler, not in `useEffect`.

# 35. A complete form example

```jsx
import { useState } from "react";

function App() {
  const [name, setName] = useState("");

  function handleChange(e) {
    setName(e.target.value);
  }

  function handleSubmit(e) {
    e.preventDefault();

    console.log("Submitted:", name);
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        value={name}
        onChange={handleChange}
        placeholder="Enter your name"
      />

      <button type="submit">
        Submit
      </button>

      <p>Your name: {name}</p>
    </form>
  );
}

export default App;
```

This example contains several important ideas:

```text
onChange
→ input event

e.target.value
→ get user input

setName()
→ update state

onSubmit
→ form submission

preventDefault()
→ prevent browser refresh
```

# Common Interview Questions

### 1. What is an event handler in React?

> An event handler is a function passed to a React element or component that React calls when a specific user interaction or browser event occurs.

### 2. How are React event names written?

Using camelCase:

```jsx
onClick
onChange
onSubmit
```

### 3. What is the difference between these?

```jsx
onClick={handleClick}
```

and:

```jsx
onClick={handleClick()}
```

The first passes the function to React.

The second executes the function immediately during rendering.

### 4. How do you pass an argument to an event handler?

Use a wrapper function:

```jsx
onClick={() => handleDelete(id)}
```

### 5. What is `event.preventDefault()`?

> It prevents the browser's default behavior for an event, such as a form submission refreshing or navigating the page.

### 6. What is `event.stopPropagation()`?

> It stops the event from propagating to ancestor elements.

### 7. `target` vs `currentTarget`?

> `target` is the element where the event originated. `currentTarget` is the element whose event handler is currently executing.

### 8. Why do we use `onSubmit` on a form instead of only `onClick` on a button?

> Because form submission can occur through several mechanisms, including pressing Enter, and `onSubmit` correctly represents the form action.

### 9. How do event handlers interact with state?

> Event handlers commonly call state updater functions. React then schedules rendering so the UI reflects the new state.

### 10. Should API requests always be inside `useEffect`?

No.

If the API request happens because the user explicitly clicked something, an event handler is often the correct place.

For example:

```jsx
async function handleSave() {
  await fetch("/api/save", {
    method: "POST"
  });
}
```

# The mental model to remember

```text
User interaction
      ↓
React event
      ↓
Event handler
      ↓
Application logic
      ↓
State update / side effect
      ↓
React rerender if needed
      ↓
UI updates
```

And memorize these common patterns:

```jsx
onClick={handleClick}
```

```jsx
onClick={() => handleDelete(id)}
```

```jsx
onChange={e => setName(e.target.value)}
```

```jsx
onSubmit={handleSubmit}
```

```js
e.preventDefault();
```

```js
e.stopPropagation();
```

If you understand those six patterns, you already understand most of the event handling you will use in beginner-to-intermediate React applications.
