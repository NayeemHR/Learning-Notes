React Fiber, Reconciliation, and the React Reconciler are closely related, but they are not the same thing.

The easiest way to understand them is:

```text
Reconciliation
     ↓
The problem/process

React Reconciler
     ↓
The system that performs that process

Fiber
     ↓
The internal architecture/data structure used by the reconciler
```

## 1. Start with the core problem

Imagine this component:

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <h1>Count: {count}</h1>
      <button onClick={() => setCount(count + 1)}>
        Increase
      </button>
    </div>
  );
}
```

Initially:

```text
count = 0
```

The UI is conceptually:

```html
<div>
  <h1>Count: 0</h1>
  <button>Increase</button>
</div>
```

Then the user clicks the button.

Now:

```text
count = 1
```

React needs to figure out:

> What exactly changed in the UI?

It should not blindly destroy everything and rebuild everything.

It needs to determine that this:

```text
Count: 0
```

became:

```text
Count: 1
```

The process React uses to determine what changed is called **reconciliation**.

---

# 2. What is Reconciliation?

Reconciliation is the process React uses to compare the previous UI tree with the newly produced UI tree and determine what needs to change.

Conceptually:

```text
Old UI
   ↓

<div>
  <h1>Count: 0</h1>
</div>
```

New UI:

```text
<div>
  <h1>Count: 1</h1>
</div>
```

React compares them:

```text
Old tree
   ↓
Compare
   ↑
New tree
```

Then concludes:

```text
<div> unchanged
<h1> unchanged
text content changed
```

So React updates only what is necessary.

That comparison process is reconciliation.

A strong interview definition is:

> Reconciliation is React's process for comparing the previous element tree with the new element tree and determining the minimum set of changes needed to update the rendered UI.

---

# 3. Reconciliation is not the DOM update itself

This distinction is important.

React first figures out what should change.

Then React actually applies those changes.

These are separate phases.

Conceptually:

```text
State update
    ↓
Render
    ↓
Reconciliation
    ↓
Determine changes
    ↓
Commit
    ↓
Update DOM
```

So:

```text
Reconciliation
≠
DOM mutation
```

Reconciliation determines the changes.

The commit phase applies them.

---

# 4. What is the React Reconciler?

The **React Reconciler** is the internal part of React responsible for handling reconciliation.

It determines things such as:

```text
Which components need work?
Which components can be reused?
Which components need to be created?
Which components need to be removed?
Which props changed?
Which state updates need processing?
Which effects need to run?
```

Think of it like React's decision-making engine.

```text
Your components
      ↓
React Reconciler
      ↓
"What changed?"
      ↓
Renderer
      ↓
Actual environment
```

That last part is important because React itself is not necessarily tied only to the browser.

---

# 5. React and ReactDOM are different

You often write:

```jsx
import React from "react";
```

and:

```jsx
import { createRoot } from "react-dom/client";
```

Why separate packages?

Because the reconciler can theoretically work with different rendering targets.

For example:

```text
React
  ↓
React Reconciler
  ↓
Renderer
```

Different renderers can target different environments.

For the browser:

```text
React
  ↓
React Reconciler
  ↓
ReactDOM
  ↓
Browser DOM
```

React Native uses a different rendering environment.

So conceptually:

> The reconciler decides what should change, while the renderer knows how to apply those changes to a specific platform.

---

# 6. Then what is React Fiber?

Fiber is the architecture React uses internally to represent and process units of work during rendering and reconciliation.

Fiber was introduced with React 16.

A useful simplified definition:

> A Fiber is an internal JavaScript object representing a unit of work associated with a React component or element.

Do not think of Fiber as something you normally write yourself.

You don't do:

```js
new Fiber();
```

Fiber is React's internal implementation.

---

# 7. Why did React need Fiber?

Before Fiber, React's older reconciliation system processed rendering more synchronously.

Imagine React has a huge component tree:

```text
App
├── Header
├── Sidebar
├── Dashboard
│   ├── Chart
│   ├── Table
│   │   ├── Row
│   │   ├── Row
│   │   ├── Row
│   │   └── 5000 more rows
│   └── Analytics
└── Footer
```

Suppose React needs to process a large amount of work.

If all of that work must happen continuously without interruption:

```text
Start work
   ↓
Process component
   ↓
Process component
   ↓
Process component
   ↓
Process thousands more
   ↓
Finish
```

The browser's main thread could remain busy.

That can hurt responsiveness.

For example, the user may:

```text
click
type
scroll
hover
```

while React is doing expensive rendering work.

Fiber made React's rendering work more flexible.

---

# 8. Fiber breaks rendering into units of work

Instead of thinking:

```text
Render entire tree as one giant task
```

think:

```text
Work A
↓
Work B
↓
Work C
↓
Work D
```

Each Fiber represents a unit of work.

Conceptually:

```text
App Fiber
   ↓
Header Fiber
   ↓
Dashboard Fiber
   ↓
Chart Fiber
   ↓
Table Fiber
```

This architecture allows React to manage rendering work more intelligently.

It supports capabilities such as:

```text
prioritizing updates
pausing render work
resuming work
restarting work
discarding obsolete work
```

This is one of the foundations behind modern concurrent React behavior.

---

# 9. What does a Fiber object represent?

Internally, React builds a tree of Fiber objects.

Very simplified:

```js
{
  type: Component,
  key: null,
  child: ...,
  sibling: ...,
  return: ...,
  pendingProps: ...,
  memoizedProps: ...,
  memoizedState: ...,
  alternate: ...
}
```

The actual implementation contains more fields.

You do not need to memorize internal field names for normal interviews.

But understanding these is useful:

```text
child
sibling
return
alternate
```

---

# 10. Fiber tree structure

Suppose your application is:

```jsx
function App() {
  return (
    <main>
      <Header />
      <Content />
      <Footer />
    </main>
  );
}
```

Conceptually, React may have Fibers representing:

```text
App
 │
 main
 │
 Header
 │
 Content
 │
 Footer
```

But internally the tree is traversable using relationships like:

```text
child
sibling
return
```

Conceptually:

```text
App
 |
child
 ↓
main
 |
child
 ↓
Header ──sibling──> Content ──sibling──> Footer
```

And:

```text
return
```

points back toward the parent.

---

# 11. Current Fiber tree and Work-in-Progress tree

This is one of the most important Fiber concepts.

React generally works with two related Fiber trees.

Conceptually:

```text
Current Tree
```

represents what is currently committed.

And:

```text
Work-In-Progress Tree
```

represents the new version React is preparing.

Example:

```text
Current

App
└── Counter: 0
```

An update happens:

```text
setCount(1)
```

React prepares:

```text
Work In Progress

App
└── Counter: 1
```

When the new work is successfully completed, React commits it.

Then the work-in-progress version becomes the current version.

---

# 12. What is `alternate`?

Fibers often have a relationship with their counterpart in the other tree.

Conceptually:

```text
Current Fiber
      ↕
   alternate
      ↕
Work-In-Progress Fiber
```

For example:

```text
Current Counter Fiber
       ↕
     alternate
       ↕
New Counter Fiber
```

Again, you normally do not interact with this directly.

But it helps explain how React can compare previous and upcoming work.

---

# 13. Render phase vs Commit phase

This is crucial.

React work can broadly be understood as two main phases.

```text
1. Render phase
2. Commit phase
```

## Render phase

React figures out:

```text
What should the new UI be?
What changed?
Which fibers need updates?
Which nodes should be inserted?
Which should be deleted?
```

This phase includes reconciliation.

Conceptually:

```text
Old Fiber tree
     +
New React elements
     ↓
Reconciliation
     ↓
Work-in-progress Fiber tree
```

The render phase can be interruptible in concurrent rendering scenarios.

---

## Commit phase

Once React knows what needs to change, it commits those changes.

For the DOM renderer, this can include:

```text
Insert DOM nodes
Update DOM attributes
Remove DOM nodes
Attach refs
Run layout-related effects
```

The commit phase is not partially applied and paused in the same way.

React needs the visible UI changes to stay consistent.

---

# 14. A full update lifecycle

Suppose:

```jsx
setCount(1);
```

A simplified flow is:

```text
1. State update is scheduled
        ↓
2. React marks relevant Fiber work
        ↓
3. Render phase begins
        ↓
4. Components are evaluated
        ↓
5. New React elements are produced
        ↓
6. Reconciler compares old and new structure
        ↓
7. Work-in-progress Fiber tree is prepared
        ↓
8. React determines required changes
        ↓
9. Commit phase
        ↓
10. DOM changes are applied
```

That is the big picture.

---

# 15. React Elements vs Fiber Nodes

Do not confuse these.

When you write:

```jsx
<User name="John" />
```

React creates a React element representation.

Conceptually it looks roughly like:

```js
{
  type: User,
  props: {
    name: "John"
  }
}
```

A React element describes what you want.

A Fiber is React's internal work object for managing that element/component during rendering.

Think:

```text
React Element
=
Description of UI
```

while:

```text
Fiber
=
Internal work unit/stateful representation used by React
```

---

# 16. Component instance vs Fiber

For modern functional components, it can be useful to think of the Fiber as carrying React's internal knowledge about that component.

For example:

```jsx
function Counter() {
  const [count, setCount] = useState(0);
}
```

You call `Counter` as a function conceptually during rendering.

But React needs to remember much more:

```text
previous state
new state
parent
children
pending work
effects
update priority
hooks
```

The Fiber node provides the internal structure React uses to track much of this work.

---

# 17. How Reconciliation compares elements

React uses several important rules.

One major rule:

> Different element types usually produce different subtrees.

Suppose previously:

```jsx
<div>
  <Counter />
</div>
```

and now:

```jsx
<section>
  <Counter />
</section>
```

The root element changed:

```text
div
↓
section
```

React may replace that subtree rather than treating the old `div` as the same element.

---

# 18. Same element type

Suppose:

Before:

```jsx
<button className="blue">
  Save
</button>
```

After:

```jsx
<button className="green">
  Save
</button>
```

The type remains:

```text
button
```

React can reuse the existing DOM element and update the changed property.

Conceptually:

```text
Same type?
    ↓
Yes
    ↓
Reuse existing node
    ↓
Update changed props
```

---

# 19. Component identity matters

Suppose:

```jsx
<Profile user="John" />
```

changes to:

```jsx
<Profile user="Sarah" />
```

The component type is still:

```text
Profile
```

So React can preserve its identity and update props.

But if:

```jsx
<Profile />
```

becomes:

```jsx
<Settings />
```

the component type changed.

React treats these as different component identities.

That can cause old state to be discarded.

---

# 20. Why keys matter in reconciliation

Consider:

```jsx
const users = ["Alice", "Bob", "Charlie"];
```

You render:

```jsx
users.map(user => (
  <User name={user} />
));
```

Then you insert:

```text
David
```

at the beginning.

Without stable keys, React has less reliable identity information.

With keys:

```jsx
users.map(user => (
  <User
    key={user.id}
    name={user.name}
  />
));
```

React can reason:

```text
Alice is still Alice
Bob is still Bob
Charlie is still Charlie
David is new
```

Keys are therefore not mainly about removing console warnings.

They are about **identity during reconciliation**.

This is a very strong interview point.

---

# 21. State preservation and keys

Consider:

```jsx
<UserProfile key="john" />
```

Then later:

```jsx
<UserProfile key="sarah" />
```

The component type is the same:

```text
UserProfile
```

but the key changed.

React treats this as a different identity.

That can reset component state.

So identity is strongly influenced by:

```text
component type
+
position
+
key
```

Keys can therefore intentionally preserve or reset state.

---

# 22. Why array index can be problematic as a key

Suppose:

```text
Index 0 → Alice
Index 1 → Bob
Index 2 → Charlie
```

Then you insert David at the beginning:

```text
Index 0 → David
Index 1 → Alice
Index 2 → Bob
Index 3 → Charlie
```

If index is the key, React may associate previous state with the wrong logical item.

That can cause strange behavior in:

```text
form inputs
animations
component-local state
checkboxes
editable lists
```

Stable IDs are usually better:

```jsx
key={user.id}
```

---

# 23. How Fiber supports priority

Not every update is equally urgent.

Consider:

```text
User typing
```

versus:

```text
Rendering a huge filtered list
```

Typing responsiveness may be more urgent.

Fiber architecture allows React's scheduler and reconciler to work with update priorities.

Conceptually:

```text
High-priority work
    ↓
User input

Lower-priority work
    ↓
Large non-urgent rendering
```

Modern React represents update priorities internally using mechanisms such as lanes.

You normally don't manipulate Fiber or lanes directly.

But features like:

```jsx
startTransition(...)
```

allow you to express priority intent through the public React API.

---

# 24. Example with `startTransition`

Imagine:

```jsx
const [input, setInput] = useState("");
const [results, setResults] = useState([]);
```

You want typing to stay responsive while updating a large list.

Conceptually:

```jsx
setInput(value);

startTransition(() => {
  setResults(expensiveSearch(value));
});
```

The first update is urgent.

The transition update is less urgent.

Fiber's architecture helps make this type of scheduling possible.

---

# 25. Can Fiber pause DOM updates?

Be precise here.

Fiber enables React to pause or restart **rendering work**.

You should not think:

> React updates half the DOM, pauses, then updates the other half later.

That would leave the UI inconsistent.

Instead:

```text
Render work
can be interrupted

Commit work
is applied consistently
```

This distinction is an excellent interview answer.

---

# 26. Why rendering must be pure

Suppose React begins rendering a component:

```jsx
function Component() {
  // ...
}
```

With concurrent rendering, React may:

```text
start rendering
pause
restart
discard work
render again
```

Therefore your render logic should not perform uncontrolled side effects.

Bad:

```jsx
function Component() {
  document.title = "Hello";

  return <div>Hello</div>;
}
```

Better:

```jsx
useEffect(() => {
  document.title = "Hello";
}, []);
```

One reason React emphasizes pure rendering is that render work may not always directly correspond to a committed UI update.

---

# 27. Reconciliation does not mean "diff the DOM"

A common misunderstanding is:

> React compares the old DOM with the new DOM.

That is not the best description.

React primarily works with its own representations.

A better mental model:

```text
Previous React/Fiber representation
        ↓
      compare
        ↑
New React element representation
```

Then the renderer applies necessary changes to the host environment.

For ReactDOM, that host environment is the browser DOM.

---

# 28. Fiber is not the Virtual DOM

Another common interview trap.

They are related ideas, but not interchangeable.

A simplified distinction:

```text
Virtual DOM
=
General idea of representing UI in memory
```

```text
Fiber
=
React's internal architecture and node structure
for scheduling, reconciliation, state, effects, and work
```

So do not answer:

> Fiber is the Virtual DOM.

That is too simplistic and technically misleading.

---

# 29. Reconciler vs Renderer

This distinction is worth memorizing conceptually.

```text
React Reconciler
```

asks:

> What needs to change?

The renderer asks:

> How do I make that change in this environment?

For ReactDOM:

```text
Reconciler:
"This button's class changed."
```

Renderer:

```text
"Update the browser DOM class attribute."
```

For another renderer, the actual platform operation may be different.

---

# 30. Fiber and Hooks

You use:

```jsx
const [count, setCount] = useState(0);
```

React needs to remember the Hook state across renders.

That information is associated internally with the component's Fiber.

Conceptually:

```text
Counter Fiber
     ↓
Hook 1 → state: 0
Hook 2 → effect
Hook 3 → ref
```

On the next render, React traverses hooks in order.

This helps explain one of React's Rules of Hooks:

```text
Do not call Hooks conditionally.
```

Bad:

```jsx
if (loggedIn) {
  const [name, setName] = useState("");
}
```

Why problematic?

React relies on consistent Hook ordering between renders.

Suppose:

```text
App
├── Header
├── Main
│   ├── Sidebar
│   └── Content
└── Footer
```

React can traverse this work approximately like:

```text
App
 ↓
Header
 ↓
Main
 ↓
Sidebar
 ↓
Content
 ↓
Footer
```

This tree traversal is implemented through Fiber relationships.

The exact implementation is considerably more complex, but this is enough to understand the architecture.

# 32. An important distinction: Render does not mean DOM update

Suppose:

```jsx
console.log("render");
```

inside a component.

You may see the component execute.

That does not guarantee React changed the DOM.

React can render:

```text
component
↓
produce result
↓
compare result
↓
discover no host changes needed
```

Or some render work can even be discarded before commit.

Therefore:

```text
Component rendered
≠
DOM definitely changed
```

This is a very useful mental model.

Here is the architecture you should remember:

```text
User interaction
      ↓
State update

      ↓
React Reconciler
      ↓
Fiber work

      ↓
Reconciliation
```

# React Fiber vs Reconciliation vs Reconciler

| Concept          | Meaning                                                                                |
| ---------------- | -------------------------------------------------------------------------------------- |
| Reconciliation   | Process of determining what changed                                                    |
| React Reconciler | React subsystem that performs reconciliation and coordinates rendering work            |
| Fiber            | Internal architecture/data structure used to represent and process units of React work |
| Renderer         | Platform-specific system that applies changes                                          |
| ReactDOM         | Browser renderer                                                                       |
| Commit phase     | Phase where calculated changes are actually applied                                    |

# Interview Questions

### 1. What is reconciliation in React?

A strong answer:

> Reconciliation is React's process of comparing the new element tree with the previous rendered tree to determine which parts of the UI need to be updated, preserved, added, or removed.

---

### 2. What is React Fiber?

> React Fiber is React's internal reconciliation architecture. A Fiber represents a unit of work associated with a component or host element and allows React to organize, prioritize, pause, resume, restart, or discard rendering work.

---

### 3. Why was Fiber introduced?

> Fiber was introduced to make React's rendering architecture more flexible. Instead of treating rendering as one indivisible synchronous task, Fiber lets React represent rendering as units of work, enabling scheduling, prioritization, interruptible rendering, and the foundation for concurrent features.

---

### 4. Is Fiber the Virtual DOM?

Strong answer:

> No. The Virtual DOM is the broader concept of representing UI in memory. Fiber is React's internal architecture and data structure for managing component work, reconciliation, state, effects, and scheduling.

---

### 5. What is the React Reconciler?

> The React Reconciler is the internal subsystem responsible for determining how a React tree should change after updates. It uses the Fiber architecture to process components and prepare changes before the renderer commits them.

---

### 6. What is the difference between the render phase and commit phase?

> During the render phase, React evaluates components and calculates the required changes. During the commit phase, React applies those changes to the host environment, such as the browser DOM. Render work may be interruptible, while committed UI mutations are applied consistently.

---

### 7. Why are keys important?

> Keys give React stable identity information when reconciling lists. They help React determine which items were added, removed, moved, or preserved, and they affect whether component state is preserved.

---

### 8. What causes React to preserve component state?

React generally preserves state when it considers the component to have the same identity.

Identity depends heavily on:

```text
same component type
same structural position
compatible key
```

Changing the key can intentionally reset state.

---

### 9. Does React rerender the entire DOM when state changes?

No.

A better answer:

> React may re-evaluate relevant components during rendering, but reconciliation determines the necessary host changes, and only those changes are committed to the DOM.

---

### 10. Can the render phase run without a commit?

Yes.

This is an important advanced point.

React can perform render work that is later:

```text
interrupted
restarted
superseded
discarded
```

So:

```text
Render
does not guarantee
Commit
```

---

If you remember only one analogy, use this:

Imagine React is an architect renovating a building.

```text
JSX / Components
=
New blueprint
```

```text
Reconciliation
=
Compare old blueprint with new blueprint
```

```text
React Reconciler
=
Engineer deciding what construction work is necessary
```

```text
Fiber
=
Work-order system that breaks the project into manageable,
prioritized units
```

```text
ReactDOM
=
Construction crew that actually changes the building
```

```text
Commit phase
=
Construction work is physically applied
```

That is much closer to how the concepts relate than simply saying "React compares the Virtual DOM."

## What you should know at your current stage

You do **not** need to memorize React source-code internals yet.

You should be able to explain these six statements clearly:

```text
1. Components produce React elements.

2. State or props changes can schedule new rendering work.

3. Reconciliation determines how the old and new UI differ.

4. The React Reconciler performs this work internally.

5. Fiber is the architecture React uses to represent and manage units of work.

6. After rendering/reconciliation finishes, the commit phase applies
   the necessary changes through the renderer.
```

If you can explain those six points without memorizing definitions, you understand React Fiber and reconciliation at a solid junior-to-intermediate level.
