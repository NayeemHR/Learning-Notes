`useEffect` becomes much easier once you understand **side effects** first. Many React beginners learn the syntax before understanding the problem it solves, which leads to using `useEffect` everywhere.

The most useful definition is:

> **`useEffect` lets a React component synchronize with something outside React after rendering.**

React's current documentation describes Effects as an “escape hatch” for synchronizing with external systems such as browser APIs, timers, network connections, and third-party libraries. ([React][1])

# 1. What is a side effect?

Consider a normal JavaScript function:

```js
function add(a, b) {
  return a + b;
}
```

If you call:

```js
add(2, 3);
```

you always get:

```text
5
```

The function doesn't change anything outside itself.

This is essentially a **pure calculation**.

Now consider:

```js
function showMessage() {
  document.title = "Hello";
}
```

This changes something outside the function:

```text
Browser document
```

That is a **side effect**.

Other examples include:

```text
Making an API request
Starting a timer
Changing document.title
Adding an event listener
Writing to localStorage
Connecting to WebSocket
Starting an animation
Interacting with a third-party library
```

The general mental model is:

```text
Pure calculation
Input → calculate → output

Side effect
Code → changes/interacts with something outside
```

# 2. Why does React care about side effects?

React expects rendering to be pure.

Consider:

```jsx
function Greeting({ name }) {
  return <h1>Hello {name}</h1>;
}
```

React should be able to call:

```jsx
Greeting({ name: "John" });
```

and simply calculate:

```jsx
<h1>Hello John</h1>
```

Nothing outside the component should unexpectedly change.

React may render components multiple times, restart rendering, or discard rendering work. This is why side effects generally should not happen directly while a component is rendering.

For example, avoid:

```jsx
function App() {
  document.title = "Dashboard";

  return <h1>Dashboard</h1>;
}
```

A better approach, when synchronization with `document.title` is actually needed, is:

```jsx
import { useEffect } from "react";

function App() {
  useEffect(() => {
    document.title = "Dashboard";
  }, []);

  return <h1>Dashboard</h1>;
}
```

# 3. There are two places side effects commonly happen

This distinction is extremely important.

Some side effects happen because the **user performed an action**.

For example:

```jsx
function Product() {
  function handleBuy() {
    fetch("/api/buy", {
      method: "POST"
    });
  }

  return (
    <button onClick={handleBuy}>
      Buy
    </button>
  );
}
```

Why should the API request happen?

Because:

```text
User clicked Buy
```

So it belongs in the **event handler**.

But consider a chat room:

```jsx
<ChatRoom roomId="general" />
```

When this component appears, you want to connect to the chat server.

There is no specific button responsible for that synchronization.

Instead:

```text
ChatRoom rendered
      ↓
Needs connection
```

That is where an Effect makes sense. React explicitly distinguishes Effects caused by rendering from event-handler side effects caused by a particular user action. ([React][1])

# 4. Basic `useEffect` syntax

```jsx
import { useEffect } from "react";

function App() {
  useEffect(() => {
    console.log("Effect executed");
  });

  return <h1>Hello</h1>;
}
```

The basic shape is:

```jsx
useEffect(() => {
  // synchronization code
}, dependencies);
```

There are two important pieces:

```text
Effect function
Dependency array
```

# 5. How `useEffect` fits into React rendering

Suppose:

```jsx
function App() {
  useEffect(() => {
    console.log("Effect");
  });

  console.log("Render");

  return <h1>Hello</h1>;
}
```

Conceptually:

```text
Component renders
       ↓
React calculates JSX
       ↓
React commits UI changes
       ↓
Effect runs
```

So remember:

```text
Render
  ↓
Commit
  ↓
Effect
```

Effects run after React commits the rendered result. ([React][1])

# 6. `useEffect` without dependency array

Example:

```jsx
useEffect(() => {
  console.log("Effect");
});
```

There is no:

```jsx
[]
```

This Effect runs after every relevant committed render of the component.

Example:

```jsx
import { useEffect, useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    console.log("Effect running");
  });

  return (
    <button
      onClick={() => setCount(count + 1)}
    >
      {count}
    </button>
  );
}
```

Conceptually:

```text
Initial render
→ Effect

Click
→ state update
→ render
→ Effect

Click
→ state update
→ render
→ Effect
```

# 7. `useEffect` with `[]`

You will frequently see:

```jsx
useEffect(() => {
  console.log("Component synchronized");
}, []);
```

The empty dependency array means the Effect has no reactive dependencies.

For normal production behavior, this corresponds to synchronization around the component being mounted.

Beginner tutorials often say:

> "`[]` means run once."

That is a useful first approximation, but it is not completely precise.

In development with React Strict Mode, React intentionally performs an extra setup-and-cleanup cycle to catch incorrect Effects. ([React][2])

So don't memorize:

```text
[] = guaranteed exactly once
```

A better mental model is:

```text
[]
=
This Effect does not depend on changing reactive values
```

# 8. `useEffect` with dependencies

Suppose:

```jsx
const [count, setCount] = useState(0);
```

Then:

```jsx
useEffect(() => {
  console.log("Count changed:", count);
}, [count]);
```

React synchronizes this Effect when `count` changes.

Conceptually:

```text
count = 0
↓
Effect

count = 1
↓
Effect

count = 2
↓
Effect
```

But changing unrelated state does not require this Effect to synchronize because the dependency is specifically:

```jsx
[count]
```

# 9. Multiple dependencies

Example:

```jsx
useEffect(() => {
  console.log(name, age);
}, [name, age]);
```

The Effect needs synchronization whenever either relevant dependency changes.

Think:

```text
name changed
→ Effect

age changed
→ Effect
```

The dependencies should reflect the reactive values used by the Effect.

# 10. A realistic example: document title

```jsx
import {
  useEffect,
  useState
} from "react";

function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    document.title = `Count: ${count}`;
  }, [count]);

  return (
    <button
      onClick={() =>
        setCount(prev => prev + 1)
      }
    >
      Count: {count}
    </button>
  );
}
```

Flow:

```text
count changes
     ↓
component renders
     ↓
React updates UI
     ↓
Effect runs
     ↓
document.title synchronized
```

Notice that `document.title` belongs to the browser, not React.

That makes this synchronization a reasonable Effect use case.

# 11. Another good use case: browser event listener

Suppose you want to detect window resizing.

```jsx
import {
  useEffect,
  useState
} from "react";

function WindowWidth() {
  const [width, setWidth] = useState(
    window.innerWidth
  );

  useEffect(() => {
    function handleResize() {
      setWidth(window.innerWidth);
    }

    window.addEventListener(
      "resize",
      handleResize
    );

    return () => {
      window.removeEventListener(
        "resize",
        handleResize
      );
    };
  }, []);

  return <p>Width: {width}px</p>;
}
```

There is an important new concept here:

```jsx
return () => {
  // cleanup
};
```

# 12. What is an Effect cleanup function?

An Effect can return another function.

```jsx
useEffect(() => {
  // setup

  return () => {
    // cleanup
  };
}, []);
```

The returned function is called the **cleanup function**.

Think:

```text
Setup
↓
Create external relationship

Cleanup
↓
Undo external relationship
```

For the event listener:

```jsx
window.addEventListener(...)
```

setup.

And:

```jsx
window.removeEventListener(...)
```

cleanup.

This symmetry is very important.

# 13. Why cleanup matters

Imagine the component appears:

```text
WindowWidth mounted
↓
resize listener added
```

Then the component disappears.

Without cleanup:

```text
Component gone
but listener may remain
```

That can create bugs or resource leaks.

With cleanup:

```text
Component no longer needs synchronization
↓
remove listener
```

React's documentation recommends that cleanup undo whatever the Effect's setup did. ([React][2])

# 14. Cleanup doesn't happen only on unmount

This is an important interview point.

Suppose:

```jsx
useEffect(() => {
  connect(roomId);

  return () => {
    disconnect(roomId);
  };
}, [roomId]);
```

Initial:

```text
roomId = "general"
↓
connect general
```

Then:

```text
roomId = "support"
```

React conceptually does:

```text
cleanup old Effect
↓
disconnect general

then

setup new Effect
↓
connect support
```

And when the component is removed:

```text
disconnect support
```

So think:

```text
Dependency changes

Old cleanup
    ↓
New setup
```

not simply:

```text
cleanup = unmount only
```

# 15. Timer example

A timer is another external system.

```jsx
import {
  useEffect,
  useState
} from "react";

function Timer() {
  const [seconds, setSeconds] = useState(0);

  useEffect(() => {
    const intervalId = setInterval(() => {
      setSeconds(prev => prev + 1);
    }, 1000);

    return () => {
      clearInterval(intervalId);
    };
  }, []);

  return (
    <p>
      Seconds: {seconds}
    </p>
  );
}
```

Setup:

```js
setInterval(...)
```

Cleanup:

```js
clearInterval(...)
```

This setup/cleanup pairing is the right mental model.

# 16. API fetching with `useEffect`

You will often see:

```jsx
import {
  useEffect,
  useState
} from "react";

function Users() {
  const [users, setUsers] = useState([]);

  useEffect(() => {
    fetch("/api/users")
      .then(response => response.json())
      .then(data => setUsers(data));
  }, []);

  return (
    <div>
      {users.map(user => (
        <p key={user.id}>
          {user.name}
        </p>
      ))}
    </div>
  );
}
```

Conceptually:

```text
Component appears
     ↓
Effect
     ↓
Request API
     ↓
Response
     ↓
setUsers()
     ↓
Render
```

Fetching inside Effects is possible, although modern React frameworks often provide better framework-specific data-fetching mechanisms. React's documentation specifically notes this distinction. ([React][3])

# 17. Fetching when a dependency changes

Imagine:

```jsx
function User({ userId }) {
```

You want data for the current user.

```jsx
useEffect(() => {
  fetch(`/api/users/${userId}`)
    .then(res => res.json())
    .then(data => setUser(data));
}, [userId]);
```

When:

```text
userId = 10
```

fetch user 10.

Later:

```text
userId = 20
```

the Effect synchronizes again and fetches user 20.

The dependency tells React:

> This synchronization depends on `userId`.

# 18. The biggest `useEffect` mistake

A common beginner thought is:

> "Something changed, therefore I need `useEffect`."

Usually false.

Consider:

```jsx
const [firstName, setFirstName] =
  useState("");

const [lastName, setLastName] =
  useState("");

const [fullName, setFullName] =
  useState("");

useEffect(() => {
  setFullName(
    `${firstName} ${lastName}`
  );
}, [firstName, lastName]);
```

This works, but it is unnecessary.

Why?

`fullName` can be calculated directly:

```jsx
const fullName =
  `${firstName} ${lastName}`;
```

Better:

```jsx
function Form() {
  const [firstName, setFirstName] =
    useState("");

  const [lastName, setLastName] =
    useState("");

  const fullName =
    `${firstName} ${lastName}`;

  return <p>{fullName}</p>;
}
```

No Effect.

No extra state.

No extra render.

React's official guidance explicitly recommends calculating derived values during rendering instead of synchronizing redundant state with an Effect. ([React][3])

# 19. Another mistake: using Effect for button actions

Suppose you write:

```jsx
const [shouldBuy, setShouldBuy] =
  useState(false);

useEffect(() => {
  if (shouldBuy) {
    buyProduct();
  }
}, [shouldBuy]);
```

Button:

```jsx
<button
  onClick={() => setShouldBuy(true)}
>
  Buy
</button>
```

This is unnecessarily indirect.

Better:

```jsx
function handleBuy() {
  buyProduct();
}

return (
  <button onClick={handleBuy}>
    Buy
  </button>
);
```

Why?

Because you know exactly why `buyProduct()` should execute:

```text
User clicked Buy
```

That belongs in the event handler.

React recommends event-specific logic in event handlers rather than Effects. ([React][3])

# 20. A very useful question

Whenever you're about to write:

```jsx
useEffect(...)
```

ask:

> **What external system am I synchronizing with?**

If your answer is:

```text
Browser API
Timer
Network connection
Third-party widget
DOM API
Subscription
WebSocket
```

an Effect may make sense.

If your answer is:

```text
"I need to calculate a value"
```

probably no Effect.

If your answer is:

```text
"The user clicked a button"
```

probably event handler.

This is the most useful rule I can give you.

# 21. Infinite loop problem

A common mistake:

```jsx
const [count, setCount] = useState(0);

useEffect(() => {
  setCount(count + 1);
}, [count]);
```

Watch what happens:

```text
count = 0
↓
Effect
↓
setCount(1)
↓
render
↓
count changed
↓
Effect
↓
setCount(2)
↓
render
↓
Effect
...
```

You created:

```text
Effect
 ↓
State update
 ↓
Render
 ↓
Effect
 ↓
State update
 ↓
Render
 ↓
∞
```

An Effect that updates one of its own dependencies requires careful reasoning.

Usually an infinite loop indicates that your Effect design needs reconsideration.

# 22. Objects and functions as dependencies

Consider:

```jsx
function App() {
  const options = {
    roomId: "general"
  };

  useEffect(() => {
    connect(options);
  }, [options]);
}
```

Each render creates a new object:

```js
{
  roomId: "general"
}
```

Even though its contents look identical, its reference is new.

Conceptually:

```text
Render 1:
options → Object A

Render 2:
options → Object B
```

Therefore the Effect can run more often than you expect.

React's documentation warns that objects and functions created inside components can cause Effects to re-run unnecessarily. ([React][2])

Usually the better solution is to restructure the Effect rather than blindly removing dependencies.

# 23. Don't lie about dependencies

Suppose:

```jsx
useEffect(() => {
  console.log(userId);
}, []);
```

but the Effect actually depends on:

```text
userId
```

It is misleading to say:

```jsx
[]
```

just because you want the Effect not to rerun.

A better version:

```jsx
useEffect(() => {
  console.log(userId);
}, [userId]);
```

Think:

> Dependencies describe your Effect's reactive inputs; they are not merely a scheduling preference.

This is a very important step toward writing correct Effects.

# 24. React Strict Mode and "useEffect runs twice"

You will eventually encounter this:

```jsx
useEffect(() => {
  console.log("Effect");
}, []);
```

During development you may see:

```text
Effect
Effect
```

and think something is broken.

If Strict Mode is enabled, React deliberately performs an additional development-only setup/cleanup cycle to detect Effects that aren't implemented safely. Production behavior is different. ([React][2])

The wrong response is usually:

```text
"How can I stop React from doing this?"
```

A better question is:

```text
"Does my cleanup correctly undo my setup?"
```

For example:

```jsx
useEffect(() => {
  const connection = connect();

  return () => {
    connection.disconnect();
  };
}, []);
```

If setup and cleanup are correct, the extra development check should not break your component.

# 25. `useEffect` vs event handler

This distinction is worth memorizing:

| Situation                          | Usually use                     |
| ---------------------------------- | ------------------------------- |
| User clicks Buy                    | Event handler                   |
| User submits form                  | Event handler                   |
| User clicks Delete                 | Event handler                   |
| Component connects to chat server  | `useEffect`                     |
| Subscribe to browser event         | `useEffect`                     |
| Start/stop timer tied to component | `useEffect`                     |
| Synchronize third-party widget     | `useEffect`                     |
| Calculate `fullName`               | Neither—calculate during render |
| Filter an array for display        | Neither—calculate during render |

This reflects React's current guidance: Effects are primarily for synchronizing with external systems, not for orchestrating ordinary application data flow. ([React][3])

# Common interview questions

**What is a side effect in React?**

A side effect is work that interacts with or changes something outside the pure rendering calculation, such as a network connection, browser API, timer, subscription, or external library.

**What is `useEffect`?**

> `useEffect` is a React Hook used to synchronize a component with an external system after React commits rendering. ([React][2])

**When does `useEffect` run?**

It runs after React commits the relevant render. Whether it synchronizes again depends on its dependencies.

**What does the dependency array do?**

It describes the reactive values used by the Effect so React knows when the synchronization needs to be repeated.

**What does an empty dependency array mean?**

It means the Effect has no changing reactive dependencies. Don't reduce this to "guaranteed exactly once," especially because Strict Mode performs an extra development setup/cleanup cycle. ([React][2])

**What is an Effect cleanup function?**

It is the function returned from an Effect that undoes the setup—for example, disconnecting a connection, removing an event listener, or clearing a timer.

```jsx
useEffect(() => {
  const id = setInterval(...);

  return () => {
    clearInterval(id);
  };
}, []);
```

**Does every state change require `useEffect`?**

No. Usually not. If a value can be calculated from props/state during rendering, calculate it directly. If something happens because of a user action, put it in the event handler. ([React][3])

**Why can `useEffect` create an infinite loop?**

If an Effect updates state that is also one of its dependencies, that update can cause another render, which runs the Effect again, creating a cycle.

# The mental model to memorize

Instead of memorizing:

```text
useEffect = run code after render
```

use this better model:

```text
              React Component
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
    Render       Events       Effects
       │            │            │
       │            │            │
 Calculate UI   User caused   Rendering caused
       │         action       synchronization
       │            │            │
       ↓            ↓            ↓
      JSX       Save/Delete   External system
```

And before writing any Effect, ask these three questions:

1. **What external system am I synchronizing with?**
2. **Which reactive values does that synchronization depend on?**
3. **Does the setup need cleanup?**

If you cannot answer the first question, there is a good chance you **do not need `useEffect`**. That principle will prevent many of the most common React bugs. ([React][1])
